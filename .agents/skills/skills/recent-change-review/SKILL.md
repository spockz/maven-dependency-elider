# Recent Change Review

Use this skill when asked to review a recent set of changes for completion, correctness, test quality, or avoidable complexity. Check whether the work undertaken or claimed complete in the selected interval fulfilled its agreed scope, including requirements with no implementation diff. Keep source files unchanged; editing, staging, and committing fixes require a request to do so. Reuse verification evidence that applies to the reviewed state and run focused checks when needed to resolve a concrete concern, following repository guidance and the user's constraints. Avoid automatically repeating the full suite when existing results suffice.

## Review window and scope

- Accept a duration such as `24h`, `3d`, or `1w`, or natural language such as “last day”, “last few days”, or “last week”. The default is 24 hours. Honor a specific start date or commit range when the user gives one.
- Resolve relative windows from the current time in UTC. Record the cutoff, branch, baseline commit, and captured `HEAD` so the scope is reproducible.
- Use committer timestamps on the current branch's first-parent history to select the window. Review the cumulative diff from the first parent of the oldest included commit in that history through the captured `HEAD`, including changes brought in by merges. If the range includes the root commit, review its initial contents too. State when merging or rewriting history brings older work into the selected range.
- Include all staged, unstaged, and untracked working-tree changes even if their age is unknown. List these separately from the time-window commit range; Git cannot reliably date uncommitted edits.
- If there are no committed or working-tree changes in scope, say so; also identify any work or completion claims explicitly supplied by the user for that interval. Review every in-scope test and implementation file, following relevant callers and helpers beyond the diff. The diff bounds the code-quality review but cannot establish that all required work was implemented. Distinguish introduced issues, pre-existing issues exposed by the changes, and omitted agreed work; keep unrelated cleanup out of scope.
- Record the working-tree state inspected. If it changes during review, revisit affected findings and coverage before reporting completion.

## Instructions and specification

Before review, read applicable `AGENTS.md` files, the relevant project brief, and the specification sources for work in scope: for example, issue or handover criteria, ADRs, API contracts, user documentation, and applicable user instructions. Follow repository guidance for supported language versions, test conventions, comments, and verification. Reconcile multiple handovers sharing an identifier against the agreed scope and amendments; titles and status labels alone cannot establish what was promised or completed. If a requirement is absent, ambiguous, or conflicts with another source, identify that uncertainty instead of inventing a contract.

## Independent Sol review

Use one newly spawned reviewer with model `gpt-6.1-sol` and `fork_turns: "none"`; honor an explicit user choice of another reviewer model. Do not reuse an agent that has seen earlier findings or implementation discussions. Provide the repository and skill paths, resolved interval and captured state, instruction/specification sources, changed-file list, and factual task requirements, including relevant user instructions absent from repository files. Include known work-item/source references, but ask the reviewer to check their coverage independently. Exclude earlier review conclusions and proposed fixes. Tell the reviewer to perform all three passes below directly, without further delegation, and return evidence with file and line locations.

If a fresh reviewer using the selected model cannot be started, report that the requested independent pass was not performed and ask whether to continue without it; do not silently substitute a reused reviewer or self-review.

### Pass 0: Completion of work in the selected interval

- Build one bounded inventory of the work undertaken or claimed complete in the interval, using the selected commits and working-tree changes, directly related handovers/specifications/closeouts, and the user's assignment. Include changes to completion records even when no production code changed. Read older specification sources when they govern this work; do not expand into an audit of unrelated historical packages or the entire backlog.
- For each relevant work item, establish the agreed delivery scope and main capabilities from the authoritative sources, including required behavior described outside a formal acceptance checklist. Check any existing requirement matrix against those sources rather than trusting its completeness. Record required acceptance criteria and explicit user-approved scope changes in a compact coverage table: `requirement/source | intended deliverable | implementation/wiring | verification evidence | status`.
- Reconcile each required capability and acceptance criterion with the captured checkout, including unchanged code, absent components, and missing production wiring. Follow the path from input through the required decision to observable output. Check that tests or other appropriate evidence would reject the capability being absent or the old behavior remaining in place. Existing adequate tests can supply evidence; a green suite, type declaration, handover, or closeout claim alone cannot prove runtime completion. Evaluate documentation-only and measurement requirements using evidence appropriate to their deliverables.
- Distinguish completed work, missing/partial implementation, implemented but unwired behavior, and implemented but unverified requirements. Identify ongoing work and explicit deferrals without calling a future milestone overdue merely because it is unfinished at the interval cutoff. Flag agreed deliverables omitted from a claimed completion. A “draft” or “review” label cannot remove a requirement the user included in the assignment; unresolved scope must be reported rather than silently excluded.
- Confirm where the evidence exists: the captured branch commit, the separately recorded uncommitted state, or a different named integration target. Report a material delivery mismatch. Investigate other refs/worktrees only when concrete evidence suggests missing integration; commit non-ancestry alone is not proof of missing work after rebasing or cherry-picking.
- Keep specification discovery at work-item level. Reuse this inventory for the test and code passes; ordinary bugs, duplicated code, regex simplifications, and local performance findings do not require a work-package history investigation. Reopen only the relevant scope sources when a finding indicates a missing capability, disconnected production path, omitted acceptance group, conflicting completion claim, or delivery mismatch. Stop that investigation once expected scope, actual state, and the gap or uncertainty are established.

### Pass 1: Test credibility and efficiency

- Derive expected behavior from the specification independently of the implementation. Reuse the completion coverage table to map each important in-scope requirement or invariant to its tests and assertions, and identify a plausible incorrect implementation those tests would reject. Check for expected values that repeat production logic or tests that still pass when the feature is broken.
- Trace fixtures through the intended production path. Check externally observable outcomes, important boundaries, refusal/error paths, and meaningful distinctions such as absent, empty, invalid, and failed results. Flag shallow mocks, accidental bypasses, and assertions that accept failure for the wrong reason. Consult implementation as needed to establish what a test actually exercises.
- Identify tests that repeat existing coverage without adding distinct observations, and integration scenarios broader than their assertions require. For any proposed consolidation or narrower test boundary, show how every distinct scenario, assertion, integration guarantee, and useful failure diagnostic remains covered.
- Apply the repository's test-efficiency policy. Look for repeated fixture generation, compilation, process startup, parsing, or production execution across compatible observations. Recommend sharing setup and read-only results across as many assertions as valid while preserving every distinct scenario and assertion. Distinguish extracting a shared helper from actually reducing the work performed.
- Check that all independent assertions can run despite another assertion failing and that collected failures fail the test. In Java, inspect JUnit `assertAll` executable boundaries: sequential assertions in one executable still stop early. Scope prerequisites and potentially failing extraction to dependent groups so unrelated observations remain executable. Check for early failures outside the aggregation.
- Check failure messages and group headings for useful context: the invariant, why equality is required, or a scenario otherwise hard to identify. Recommend JUnit messages and `assertAll` headings, or AssertJ `.as(...)` before the assertion, only where they add that information. Flag labels that merely repeat the comparison or replace useful expected/actual diagnostics; construct expensive diagnostic text lazily.
- Verify that shared fixtures remain immutable or mutations use isolated copies, with valid resource lifetimes and cleanup. Check order independence, concurrent execution, and timing/environment dependencies. Account for the effect of consolidation on parallelism and diagnostics; substantiate speedup claims with comparable timings and preserved scenario/assertion coverage.

### Pass 2: Implementation quality and runtime work

- Trace representative execution paths across components for repeated scanning, parsing, archive access, hashing, normalization, regex compilation, or validation of the same inputs. Identify call sites, execution frequency, and the lifetime over which reuse is valid. Account for invalidation, memory use, and concurrency before proposing caching. Ground performance concerns in a concrete path and workload; distinguish measurement from inference.
- Check both source duplication and differently written implementations of the same rule. Inspect duplicate domain representations, redundant state, obsolete fallback paths, and pass-through wrappers. Verify callers and configured or reflective entry points before declaring code unused. Recommend the smallest coherent design that satisfies current requirements, preserving concepts with different semantics.
- Review production and test code explicitly for overengineering against the agreed requirements and actual usage. Look for speculative extension points, generic frameworks for narrow tasks, unnecessary abstraction or configuration layers, and state or lifecycle machinery without a concrete need. For each finding, explain the maintenance or runtime cost and propose a simpler design, including its tradeoffs. Preserve required behavior, meaningful domain boundaries, testability, and correctness safeguards. Neither an abstraction with one implementation nor a high class or line count alone proves overengineering; show which complexity can be removed without losing a supported capability or invariant.
- Check resource ownership and closure, shared mutable state, cache keys and lifetime, deterministic output, and failure propagation. Verify that changes preserve public contracts, persisted formats, and the repository's compatibility policy.
- For regex consolidation, preserve matching mode, anchors, flags, capture behavior, and precedence; consider backtracking cost and simpler literal operations where appropriate. For conditional consolidation, preserve short-circuit evaluation, side effects, exception behavior, and ordering. Explain the equivalence and clarity benefit of each proposal; fewer patterns or branches alone do not establish an improvement.
- Assess modern Java against the configured source/runtime level and repository conventions. Favor idioms that remove unnecessary state or boilerplate and improve clarity or correctness. Evaluate conciseness by the complexity a reader must understand and maintain.

After receiving the review, verify proposed findings against the cited code and specification, reconcile disagreements using evidence, and check both requirement coverage and coverage of every in-scope test and implementation file. Missing work may have no changed line: cite its source criterion and the expected implementation boundary or unchanged behavior. Preserve unresolved uncertainty and identify unreviewed areas; do not claim a complete review when material areas remain unexamined.

## Report

Return a concise review receipt containing:

- The UTC cutoff, baseline and captured `HEAD`, and separately listed working-tree changes.
- The instruction/specification sources read, coverage of the selected scope, and any unreviewed areas.
- A completion verdict for the work in the selected interval, with a compact requirement-coverage summary and significant missing, partial, unwired, unverified, deferred, or undelivered work. Distinguish completeness of the delivered work from completeness of this review. If no authoritative scope can be established, say that completion could not be verified.
- Test findings first, then implementation findings. Each finding needs severity, precise file/line evidence, a concrete scenario or execution path, impact, and a focused remedy with its tradeoffs. Cite both sides of duplication and identify whether an issue is introduced or pre-existing.
- Requirement-to-test gaps and proposed reductions in test/runtime work, explaining which observations and assertions are preserved. Separate required corrections from optional improvements and measured costs from inference. Group symptoms of one missing capability into one completion finding with supporting examples, and cross-reference overlapping code findings; do not duplicate it as a separate bug for every affected call site or invent findings to fill categories.
- A clear verdict within the reviewed scope, including what was inspected, executed, and remains unverified.

Do not modify repository files to save the receipt unless the user asks for a file artifact.
