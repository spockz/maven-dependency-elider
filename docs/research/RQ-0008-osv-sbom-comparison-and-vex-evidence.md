# RQ-0008: OSV SBOM Comparison and VEX Evidence

## Status

Open

## Current boundary

The Maven plugin emits a post-elision CycloneDX SBOM when configured trimming runs. The core and plugin now ingest typed OSV-owned record groups from the schema-v1 cache. **Updated proof-admission finding (2026-10-31):** only a validated `HIGH` assertion declared in the effective project POM can supply omitted-code or precondition proof inputs. Cached/advisory or heuristic rows do not become proof evidence because their confidence label says `HIGH`; configured POM `LOW`/`MEDIUM` rows also remain review-only. Structured file/routine candidates remain `MEDIUM` review evidence; exact-version Java source lookup, complete class-set attribution, dual-source range comparison, and broad CNA range semantics remain deferred. Unresolved candidates should lead to owner verification plus an explicit POM assertion. The existing proof engines still enforce archive identity/digests or ADR-0008's complete inventory boundary. Conflicting applicable mappings suppress VEX evidence and report classifications. OSV-Scanner package findings remain package-level and do not identify which class or method a CVE affects.

**S2 implementation status (2026-11-01; review pending):** exact source/build correspondence is implemented as non-authoritative evidence, not a new proof authority. Maven's exact-version `sources` classifier is a locator only; the result binds its bytes and resolution provenance to the exact assessed GAVCE and original ordinary unclassified JAR digest/inventory. Reproduction admits only the pinned Oracle GraalVM JDK 21.0.12+7.1 image, fixed processor/plugin-free compiler options, one explicit source unit per isolated task, and byte-identical output path/content equality with the entire physical original-JAR inventory. A nonempty original manifest `Class-Path` is rejected. The false-by-default conventional-layout flag authorizes only the documented path-root translation. Routine-only claims require one declaration owner across the complete exact-version sources archive; overloads/repeated names abstain. MRJAR, modules, generated/transforming builds, and unsupported compiler settings abstain. Focused tests and Java lint pass; independent review remains pending. S2 correspondence cannot feed proof until a later S3 live-byte validation. See the [WP-VEX-02 implementation ledger](../../.scratch/orchestration-status.md#s2-sourcebuild-correspondence-implementation-review-pending).

## Track 3 evidence status

The external `make scan-sbom` harness compares machine-readable OSV-Scanner results for the example's baseline and post-elision CycloneDX inventories. It records a common scanner executable/version, separate start and completion timestamps for each scan, the SHA-256 of each input SBOM, the raw scan JSON, and the package-level delta. Each SBOM is hashed before and after its scan; a changed file aborts comparison, and classification uses the in-memory inventory parsed from the bytes whose hash is recorded. It requests offline vulnerability matching so both scans use the scanner's shared local cache. OSV-Scanner does not expose a database revision in this workflow, so identical database contents are not claimed or independently verified. The harness accepts exit status `1` only when valid JSON contains findings and accepts status `0` only when JSON has no findings; inconsistent output, other nonzero statuses, malformed JSON, and status `1` without findings are execution/result errors. A finding is called eliminated only if the associated component is absent from the post-elision SBOM; if that component remains but the finding is not returned, the report labels it separately. Older OSV-Scanner output without PURLs is resolved against the input inventory by Maven coordinate and version; if multiple PURL variants match, the finding remains unclassified.

An eliminated finding means that the baseline package finding did not match a package finding in the post-elision inventory. It is not evidence that vulnerable code was removed or that a product is unaffected, and the harness emits no VEX. This resolves the decoupled CI workflow question in favor of an external comparison gate while leaving VEX eligibility subject to the separate symbol-evidence gates below.

## Research questions

1. Should the plugin optionally invoke OSV-Scanner against both a baseline SBOM and the post-elision SBOM, or should scanning remain an external CI step?
2. If it is integrated, how should scanner version, vulnerability database revision/time, target inventory, and outputs be recorded so pre/post results are comparable and reproducible?
3. Can the difference be reported only as findings no longer matched to the post-elision component inventory, without implying exploitability or code-level remediation?
4. What should happen when the scanner, network, or vulnerability database is unavailable: skip explicitly, warn, or fail? How can offline use remain clear and auditable?
5. Is there reliable vulnerability data that maps a CVE to specific classes or members, and can that map be linked to verified trim output strongly enough to support `code_not_present` VEX? The dual-source OSV/CVEList architecture is accepted in [ADR-0006](../adr/0006-dual-source-vulnerability-advisory-ingestion-from-cvelist-v5-and-osv-maven.md), but complete exact-version Java source-to-class attribution remains deferred; structured candidates stay review-only until it is proven.
6. How should advisories mapping multiple vulnerable classes be interpreted across wide version ranges? For instance, Jackson Core `CVE-2026-68494` maps both `ByteArrayFeeder` and `StreamConstraintsException`, but `StreamConstraintsException` only exists in versions >= 2.15 while versions < 2.15 are also marked vulnerable. Does the presence of any mapped class indicate vulnerability, or must all be present? Under what conditions can current fail-closed strictness be relaxed?

## Options

1. Keep scanner execution external. Users scan the generated SBOM or final package in their CI security stage and retain scanner-owned results.
2. Add opt-in plugin orchestration for pinned scanner versions and explicit pre/post inventories, but emit package-level finding deltas only.
3. Add VEX generation only when a vulnerability-to-code mapping and verified evidence support the chosen VEX status and justification. Omitted-code and precondition proof, assessment, serialization, and transactional Maven publication are implemented.

## Benefits and costs

Integration could make the tested post-elision inventory easier to assess and could show which package findings no longer match that inventory. It adds scanner startup time, network/database access or database maintenance, version and database drift, output storage, and policy for failures and offline builds. A changed or missing package finding is only an inventory delta; it does not prove that vulnerable code was removed or that the product is unaffected.

## Evidence gates

- Compare scans of explicitly identified baseline and post-elision CycloneDX inventories using the same scanner version and a recorded database revision or timestamp.
- Label results as package-level findings; do not infer class-level status from an absent package finding or an elision decision.
- Generate omitted-code VEX only from a validated `HIGH` assertion declared in the effective project POM, bound to the exact matched component/version, when verified trim evidence establishes the mapped classes absent from the final component. Cached/advisory or heuristic `HIGH` labels and configured POM `LOW`/`MEDIUM` rows are not proof inputs. A separate precondition proof uses the same POM admission gate and requires both the exact prerequisite Maven coordinate and fully qualified class absent from the complete declared inventory. Require explicit `elide.preconditionClassPathComplete=true` opt-in. The captured inventory must include declared application classes/resources and every effective post-elision dependency archive, with an inventory fingerprint and per-file digests revalidated during proof. Unknown or unreadable inputs, incomplete source/resource discovery, the class in any inventoried provider, a digest mismatch, or an ambiguous mapping suppresses the statement. This proves absence only within the declared Maven inventory; providers introduced later by packaging or deployment remain outside the claim. Scanner findings alone must produce no VEX statement.
- Test positive and fail-closed cases for both proof kinds, including version-level findings that remain after trimming, coordinate-only mappings, equivalent classes in other dependencies or application providers, incomplete inventories, and digest mutation.
- Core omitted-code proof requires bound explicit owner evidence for exact group, artifact, version, type, and classifier identity, matching archive digests, mapped classes present in the original, and mapped plus original nested classes absent from the trimmed archive. Scope is ignored for package identity. Maven assessment applies `versionRangeSpec` before binding proof evidence.
- Strict JSON input rejects unknown/duplicate fields and trailing documents. Cache refresh validates configured HTTP(S) URIs, uses bounded lock/body waits, streamed temporary files, atomic replacement, and cache/seed fallback. The Maven goal defaults to OSV Maven snapshot and CVEList v5 URIs and refreshes missing or stale cache content unless Maven is offline. Explicit POM mappings remain supported and override cached entries; the bundled seed is empty.
- Core mapping metadata, the complete-inventory proof model, serializers, Maven snapshot-aware assessment, and transactional goal publication are implemented. The assessment rejects conflicting applicable evidence before proof selection, coalesces equivalent overlapping mappings, normalizes identity without Maven scope, and keeps conservative omission and inactive classifications mutually exclusive. The goal requires the explicit completeness opt-in, captures the inventory after planning, and aborts publication if revalidation finds changed provider membership or content. Scanner orchestration remains separate. The core proof requires a caller-supplied complete inventory and does not prove absence of providers introduced outside the declared Maven build inventory; serializers recheck the exact affected component path and file digest.
- The focused admission regression uses the same physically successful trim record for explicit-POM `HIGH`, configured-POM `LOW`/`MEDIUM`, and cache-only `HIGH`. Only the validated POM `HIGH` may emit attestation and proven-absent classification; the other scenarios assert both outputs remain empty. Structured source attribution remains review-only until complete exact-version class-set proof is available.

**Typed production ingestion status (2026-10-31):** the schema-v1 codec is used by the OSV indexer, cache manager, seed, update goal, validators, and Maven assessment. Cache records preserve OSV identity and aliases, complete Maven ecosystem/package names and raw OSV affected data including range repositories, separate prose/URL origins, and CNA affected-entry identities, default status, version type/status/bounds/ordered changes, machine package identity, file claims, and object-shaped routine names. Records without CVE aliases retain their OSV package contexts without fabricating CVEs. Assessment retains exact Maven package identity contexts from matched OSV records separately from CVE-scoped evidence, so package-only groups remain available without creating a CVE finding or proof. Structured candidates attach to an OSV scope only on an exact machine-readable Maven package URL match; display-name similarity alone does not establish identity, and unmatched claims remain in their CNA entry without a scope association. Candidates remain review-only; this does not establish exact version alignment, dual-source range agreement, source-to-bytecode attribution, or a complete class set. Persisted cache evidence never enters the proof APIs; effective POM declarations remain the only proof authority. Incremental delta endpoints are currently disabled; refresh uses a full snapshot and naturally removes withdrawn records. Malformed records, duplicate JSON keys/record IDs, trailing documents, invalid nested model claims, and incomplete ZIP directory data are rejected before publication; failures retain the previous cache and freshness state or use the typed seed fallback. The partial-delta and range findings remain open, and producer identity/build-identity gates remain deferred. The cache is not converted to the former flat `VulnerabilitySymbolMapping` format; old flat cache data is rejected and rebuilt online or replaced by typed-seed fallback with a diagnostic offline.

## Implemented evidence and architectural alignment

### Approved synchronization follow-up (2026-11-01)

[WP-VEX-03](../handovers/2026-11-01-wp-vex-03-osv-snapshot-and-delta-synchronization.md) and the 2026-11-01 [ADR-0006 amendment](../adr/0006-dual-source-vulnerability-advisory-ingestion-from-cvelist-v5-and-osv-maven.md#dated-amendment-2026-11-01-snapshot-and-delta-synchronization) specify full Maven ZIP reconstruction followed by modified-ID reconciliation at the existing invocation-driven refresh cadence. This is approved scope with implementation evidence pending; the snapshot-only status above remains the runtime baseline, and the partial-delta finding remains open.

The contract preserves each record's `modified` timestamp, replaces whole records and derived Maven associations by OSV ID, and commits snapshot/delta/metadata together or preserves the prior state. `zipLastModified` comes only from the HTTP metadata for the downloaded ZIP; `lastSyncTimestamp` is local successful synchronization time used for the default 24-hour TTL. Local download/file time is not a substitute for source time. Malformed source metadata, incomplete CSV/record retrieval and publication failures cannot advance committed freshness.

The CSV supplies revision candidates, not deletion events. Full snapshot replacement reconciles deletion or moves out of Maven; records sharing CVE aliases or coordinates retain independent ownership. Independent exports have no documented common watermark, so neither ZIP time nor local sync time establishes global source coverage. The intended refresh opportunity is 24 hours plus the next invocation, with additional upstream/offline/failure delay possible; zero-lag freshness is not promised.

Required evidence is recorded in the handover's owned matrix: HTTP metadata and per-record timestamp preservation; exact OSV-ID replacement; unsorted/duplicate CSV handling; source removals and withdrawals; partial-request and publication rollback; invocation cadence/force/offline behavior; and unchanged proof admission. No production or test implementation is claimed by this documentation. The external scanner's missing database revision remains a separate limitation and is not resolved by adding plugin-cache timestamps.

### Existing proof and ingestion evidence

The proof API is constrained by the per-JAR provenance and original-artifact immutability invariants in [ADR-0003, Invariants](../adr/0003-proguard-core-intra-jar-trimming-and-cyclonedx-pedigree.md#invariants). The core precondition model is implemented in [PreconditionClassInventory.java](../../elider-core/src/main/java/io/github/spockz/elider/model/PreconditionClassInventory.java) and [PreconditionProof.java](../../elider-core/src/main/java/io/github/spockz/elider/model/PreconditionProof.java). [ADR0008PreconditionProofTest.java](../../elider-core/src/test/java/io/github/spockz/elider/model/ADR0008PreconditionProofTest.java) covers exact-class absence, dependency and application providers, source-name/digest binding, incomplete inventories, mutation, and malformed inputs. [MavenVulnerabilityAssessment.java](../../dependency-elider-maven-plugin/src/main/java/io/github/spockz/elider/plugin/MavenVulnerabilityAssessment.java) applies complete-inventory proofs to exact retained candidates and classifies only successful proofs as inactive; [ADR0008MavenPreconditionAssessmentTest.java](../../dependency-elider-maven-plugin/src/test/java/io/github/spockz/elider/plugin/ADR0008MavenPreconditionAssessmentTest.java) is Surefire-selectable and covers exact version selection, overlapping mapping order/conflicts, confidence and incomplete metadata, POM overrides, scope-free precedence, opt-out diagnostics, report category separation, and conservative-omission reconciliation. The opt-in Maven snapshot implementation in [MavenPreconditionInventory.java](../../dependency-elider-maven-plugin/src/main/java/io/github/spockz/elider/plugin/MavenPreconditionInventory.java) captures declared source, output, and resource providers and revalidates root membership and digests; [ADR0008MavenPreconditionInventoryTest.java](../../dependency-elider-maven-plugin/src/test/java/io/github/spockz/elider/plugin/ADR0008MavenPreconditionInventoryTest.java) covers source/output/resource providers, generated-name limitations, unknown filesystem entries, strict artifact failures, and snapshot mutation. [ADR0008MavenPreconditionPublicationTest.java](../../dependency-elider-maven-plugin/src/test/java/io/github/spockz/elider/plugin/ADR0008MavenPreconditionPublicationTest.java) covers shared-snapshot publication, output drift, stale-output ownership, and transactional rollback.

Core CycloneDX and OpenVEX serializers support the precondition attestation. [ADR0008PreconditionVexSerializationTest.java](../../elider-core/src/test/java/io/github/spockz/elider/metadata/ADR0008PreconditionVexSerializationTest.java) is Surefire-selectable and checks both schemas, exact post-inventory component and digest binding, omitted-code precedence, and order-independent conflict rejection. Maven publication revalidates the complete provider inventory before replacing outputs; the serializers independently rehash the affected component file.

Typed advisory ingestion and refresh are implemented in [AdvisoryEvidenceReader.java](../../elider-core/src/main/java/io/github/spockz/elider/scanner/AdvisoryEvidenceReader.java), [AdvisoryEvidenceWriter.java](../../elider-core/src/main/java/io/github/spockz/elider/scanner/AdvisoryEvidenceWriter.java), [OsvSnapshotIndexer.java](../../elider-core/src/main/java/io/github/spockz/elider/scanner/OsvSnapshotIndexer.java), and [VulnerabilityCacheManager.java](../../elider-core/src/main/java/io/github/spockz/elider/scanner/VulnerabilityCacheManager.java). Their focused tests cover strict v1 documents, OSV record ownership, multiple CNA products, package-only retention, separate origins, unresolved structured candidates, invalid-cache online/offline behavior, full-snapshot withdrawal, and publication failure preservation.

## Decision requested

Determine whether optional scanner orchestration provides enough reproducibility and workflow value to justify its compute, network/database, and failure-policy costs. Keep package-level comparison and evidence-backed VEX generation as separate capabilities.
