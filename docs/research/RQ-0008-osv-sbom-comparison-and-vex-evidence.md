# RQ-0008: OSV SBOM Comparison and VEX Evidence

## Status

Open

## Current boundary

The Maven plugin emits a post-elision CycloneDX SBOM when configured trimming runs. The core and plugin ingest typed OSV-owned record groups from the schema-v1 cache. **WP-VEX-02 proof-admission update (2026-11-01):** validated explicit POM `HIGH` assertions and a distinct live-verified structured CNA capability can supply omitted-code proof. Cache, heuristic and package-only rows do not become proof evidence because a confidence label says `HIGH`; configured POM `LOW`/`MEDIUM` rows remain review-only. Structured proof requires one exact CNA product entry and concrete Maven version with current OSV and CNA applicability agreeing, followed by complete exact-version Java source-to-bytecode reproduction and the existing physical omission checks. The supported automatic path is limited to ordinary non-MRJAR Java sources reproduced with the exact pinned Oracle GraalVM JDK 21.0.12+7.1 compiler image and fixed options; unsupported or ambiguous cases remain review-only. This trusts the CNA's declared affected files/routines and does not independently validate vulnerability truth or declaration completeness. The configured producer-compatible typed OSV index is the selected OSV source, not an independent verification of raw upstream OSV bytes. Existing proof engines still enforce archive identity/digests or ADR-0008's complete-inventory boundary. Conflicting applicable mappings suppress VEX evidence and report classifications. OSV-Scanner package findings remain package-level and do not identify which class or method a CVE affects.

**S2 correspondence checkpoint (2026-11-01; reviewed GO at `f9131c8`):** exact source/build correspondence was first implemented as non-authoritative evidence. Its source-classifier locator, exact artifact binding, pinned compiler, complete output equality, and conservative layout/routine rules remain in force. The checkpoint statement that correspondence could not feed proof until live-byte validation was completed by later S3/S4 slices; the current proof boundary is summarized above and tracked in the [WP-VEX-02 implementation ledger](../../.scratch/orchestration-status.md#wp-vex-02-typed-evidence-continuation-requirement-to-evidence-matrix).

## Track 3 evidence status

The external `make scan-sbom` harness compares machine-readable OSV-Scanner results for the example's baseline and post-elision CycloneDX inventories. It records a common scanner executable/version, separate start and completion timestamps for each scan, the SHA-256 of each input SBOM, the raw scan JSON, and the package-level delta. Each SBOM is hashed before and after its scan; a changed file aborts comparison, and classification uses the in-memory inventory parsed from the bytes whose hash is recorded. It requests offline vulnerability matching so both scans use the scanner's shared local cache. OSV-Scanner does not expose a database revision in this workflow, so identical database contents are not claimed or independently verified. The harness accepts exit status `1` only when valid JSON contains findings and accepts status `0` only when JSON has no findings; inconsistent output, other nonzero statuses, malformed JSON, and status `1` without findings are execution/result errors. A finding is called eliminated only if the associated component is absent from the post-elision SBOM; if that component remains but the finding is not returned, the report labels it separately. Older OSV-Scanner output without PURLs is resolved against the input inventory by Maven coordinate and version; if multiple PURL variants match, the finding remains unclassified.

An eliminated finding means that the baseline package finding did not match a package finding in the post-elision inventory. It is not evidence that vulnerable code was removed or that a product is unaffected, and the harness emits no VEX. This resolves the decoupled CI workflow question in favor of an external comparison gate while leaving VEX eligibility subject to the separate symbol-evidence gates below.

## Research questions

1. Should the plugin optionally invoke OSV-Scanner against both a baseline SBOM and the post-elision SBOM, or should scanning remain an external CI step?
2. If it is integrated, how should scanner version, vulnerability database revision/time, target inventory, and outputs be recorded so pre/post results are comparable and reproducible?
3. Can the difference be reported only as findings no longer matched to the post-elision component inventory, without implying exploitability or code-level remediation?
4. What should happen when the scanner, network, or vulnerability database is unavailable: skip explicitly, warn, or fail? How can offline use remain clear and auditable?
5. Is there reliable vulnerability data that maps a CVE to specific classes or members, and can that map be linked to verified trim output strongly enough to support `code_not_present` VEX? The dual-source OSV/CVEList architecture is accepted in [ADR-0006](../adr/0006-dual-source-vulnerability-advisory-ingestion-from-cvelist-v5-and-osv-maven.md). WP-VEX-02 now implements live exact-version Java source/build attribution and a distinct structured proof capability. That capability trusts the CNA's declared affected file/routine set; whether future sources can independently verify vulnerability truth or list completeness remains open.
6. How should advisories mapping multiple vulnerable classes be interpreted across wide version ranges? For instance, Jackson Core `CVE-2026-68494` maps both `ByteArrayFeeder` and `StreamConstraintsException`, but `StreamConstraintsException` only exists in versions >= 2.15 while versions < 2.15 are also marked vulnerable. Does the presence of any mapped class indicate vulnerability, or must all be present? Under what conditions can current fail-closed strictness be relaxed?

## Options

1. Keep scanner execution external. Users scan the generated SBOM or final package in their CI security stage and retain scanner-owned results.
2. Add opt-in plugin orchestration for pinned scanner versions and explicit pre/post inventories, but emit package-level finding deltas only.
3. Add VEX generation only when a vulnerability-to-code mapping and verified evidence support the chosen VEX status and justification. Omitted-code and precondition proof, assessment, serialization, and transactional Maven publication are implemented.

## Benefits and costs

Integration could make the tested post-elision inventory easier to assess and could show which package findings no longer match that inventory. It adds scanner startup time, network/database access or database maintenance, version and database drift, output storage, and policy for failures and offline builds. A changed or missing package finding is only an inventory delta; it does not prove that vulnerable code was removed or that the product is unaffected.

## Evidence gates

- Compare scans of explicitly identified baseline and post-elision CycloneDX inventories using the same scanner version and a recorded database revision or timestamp.
- Label results as package-level findings; do not infer class-level status from an absent package finding or an elision decision.
- Generate omitted-code VEX only from either a validated effective-POM `HIGH` assertion or the separate live-verified structured CNA capability, each bound to the exact component and current physical evidence. The structured path additionally requires one exact CNA product/version whose current OSV and CNA scopes agree, complete exact-version source-to-bytecode attribution, and proof that every mapped class is absent from the trimmed artifact. Cached/advisory or heuristic `HIGH` labels and configured POM `LOW`/`MEDIUM` rows are not proof inputs. A separate precondition proof requires both the exact prerequisite Maven coordinate and fully qualified class absent from the complete declared inventory, with explicit `elide.preconditionClassPathComplete=true` opt-in. The captured inventory must include declared application classes/resources and every effective post-elision dependency archive, with an inventory fingerprint and per-file digests revalidated during proof. Unknown or unreadable inputs, incomplete source/resource discovery, the class in any inventoried provider, a digest mismatch, or an ambiguous mapping suppresses the statement. This proves absence only within the declared Maven inventory; providers introduced later by packaging or deployment remain outside the claim. Scanner findings alone must produce no VEX statement.
- Test positive and fail-closed cases for both proof kinds, including version-level findings that remain after trimming, coordinate-only mappings, equivalent classes in other dependencies or application providers, incomplete inventories, and digest mutation.
- Explicit-POM omitted-code proof requires bound owner evidence for exact group, artifact, version, type, and classifier identity, matching archive digests, mapped classes present in the original, and mapped plus original nested classes absent from the trimmed archive. Structured omitted-code proof uses a separate live-verified capability and additionally requires exact dual-source product/version applicability and complete source-to-bytecode attribution. Both paths apply the same physical omission and digest guards. Scope is ignored for package identity, and Maven assessment applies `versionRangeSpec` before binding explicit POM evidence.
- Strict JSON input rejects unknown/duplicate fields and trailing documents. Cache refresh validates configured HTTP(S) URIs, uses bounded lock/body waits, streamed temporary files, atomic replacement, and cache/seed fallback. The Maven goal defaults to OSV Maven snapshot and CVEList v5 URIs and refreshes missing or stale cache content unless Maven is offline. Explicit POM mappings remain supported and override cached entries; the bundled seed is empty.
- Core mapping metadata, the complete-inventory proof model, serializers, Maven snapshot-aware assessment, and transactional goal publication are implemented. The assessment rejects conflicting applicable evidence before proof selection, coalesces equivalent overlapping mappings, normalizes identity without Maven scope, and keeps conservative omission and inactive classifications mutually exclusive. The goal requires the explicit completeness opt-in, captures the inventory after planning, and aborts publication if revalidation finds changed provider membership or content. Scanner orchestration remains separate. The core proof requires a caller-supplied complete inventory and does not prove absence of providers introduced outside the declared Maven build inventory; serializers recheck the exact affected component path and file digest.
- The focused admission regression uses the same physically successful trim record for explicit-POM `HIGH`, configured-POM `LOW`/`MEDIUM`, and cache-only `HIGH`. Only validated explicit POM `HIGH` or the distinct live-verified structured capability may emit omitted-code attestation; cache-only/heuristic `HIGH` and configured POM `LOW`/`MEDIUM` remain ineligible. Both paths still pass the same physical artifact and digest checks.

**Typed production ingestion checkpoint (2026-10-31; before the S3/S4 implementation):** the schema-v1 codec is used by the OSV indexer, cache manager, seed, update goal, validators, and Maven assessment. Cache records preserve OSV identity and aliases, complete Maven ecosystem/package names and raw OSV affected data including range repositories, separate prose/URL origins, and CNA affected-entry identities, default status, version type/status/bounds/ordered changes, machine package identity, file claims, and object-shaped routine names. Records without CVE aliases retain package contexts without fabricating CVEs. Structured candidates attach to an OSV scope only on exact machine-readable Maven package identity; unmatched claims remain in their CNA entry without an inferred scope. At that checkpoint, live source attribution, reports, and producer gates were still future slices. The later implementation status is recorded at the top of this RQ and in the [WP-VEX-02 matrix](../../.scratch/orchestration-status.md#wp-vex-02-typed-evidence-continuation-requirement-to-evidence-matrix). The configured producer-compatible typed OSV index remains the selected OSV source, not independent verification of raw upstream OSV. Incremental delta synchronization and broad CNA range semantics remain separate research. Unreleased cache formats stay at schema version 1.

## Implemented evidence and architectural alignment

### Approved synchronization follow-up (2026-11-01)

[WP-VEX-03](../handovers/2026-11-01-wp-vex-03-osv-snapshot-and-delta-synchronization.md) and the 2026-11-01 [ADR-0006 amendment](../adr/0006-dual-source-vulnerability-advisory-ingestion-from-cvelist-v5-and-osv-maven.md#dated-amendment-2026-11-01-snapshot-and-delta-synchronization) specify full Maven ZIP reconstruction followed by modified-ID reconciliation at the existing invocation-driven refresh cadence. Implementation, local verification, dedicated review, and integration are complete as recorded in the handover. The operational limits below remain: no shared source watermark, no CSV deletion feed, and eventual consistency rather than a zero-lag guarantee.

The contract preserves each record's `modified` timestamp, replaces whole records and derived Maven associations by OSV ID, and commits snapshot/delta/metadata together or preserves the prior state. `zipLastModified` comes only from the HTTP metadata for the downloaded ZIP; `lastSyncTimestamp` is local successful synchronization time used for the default 24-hour TTL. Local download/file time is not a substitute for source time. Malformed source metadata, incomplete CSV/record retrieval and publication failures cannot advance committed freshness.

The CSV supplies revision candidates, not deletion events. Full snapshot replacement reconciles deletion or moves out of Maven; records sharing CVE aliases or coordinates retain independent ownership. Independent exports have no documented common watermark, so neither ZIP time nor local sync time establishes global source coverage. The intended refresh opportunity is 24 hours plus the next invocation, with additional upstream/offline/failure delay possible; zero-lag freshness is not promised.

The handover's owned matrix records verified implementation evidence for HTTP metadata and per-record timestamp preservation; exact OSV-ID replacement; unsorted/duplicate CSV handling; source removals and withdrawals; partial-request and publication rollback; invocation cadence/force/offline behavior; and unchanged proof admission. The external scanner's missing database revision remains a separate limitation and is not resolved by adding plugin-cache timestamps.

### Existing proof and ingestion evidence

The proof API is constrained by the per-JAR provenance and original-artifact immutability invariants in [ADR-0003, Invariants](../adr/0003-proguard-core-intra-jar-trimming-and-cyclonedx-pedigree.md#invariants). [OmittedCodeProof.java](../../elider-core/src/main/java/io/github/spockz/elider/model/OmittedCodeProof.java) verifies exact artifact identity and recorded digests before and after inspecting each archive; [OmittedCodeProofTest.java](../../elider-core/src/test/java/io/github/spockz/elider/model/OmittedCodeProofTest.java) covers successful proof, surviving mapped and nested classes, digest mutation, identity mismatch, and a mapped class absent from the original.

The core precondition model is implemented in [PreconditionClassInventory.java](../../elider-core/src/main/java/io/github/spockz/elider/model/PreconditionClassInventory.java) and [PreconditionProof.java](../../elider-core/src/main/java/io/github/spockz/elider/model/PreconditionProof.java). [ADR0008PreconditionProofTest.java](../../elider-core/src/test/java/io/github/spockz/elider/model/ADR0008PreconditionProofTest.java) covers exact-class absence, dependency and application providers, source-name/digest binding, incomplete inventories, mutation, and malformed inputs. [MavenVulnerabilityAssessment.java](../../dependency-elider-maven-plugin/src/main/java/io/github/spockz/elider/plugin/MavenVulnerabilityAssessment.java) applies complete-inventory proofs to exact retained candidates and classifies only successful proofs as inactive; [ADR0008MavenPreconditionAssessmentTest.java](../../dependency-elider-maven-plugin/src/test/java/io/github/spockz/elider/plugin/ADR0008MavenPreconditionAssessmentTest.java) is Surefire-selectable and covers exact version selection, overlapping mapping order/conflicts, confidence and incomplete metadata, POM overrides, scope-free precedence, opt-out diagnostics, report category separation, and conservative-omission reconciliation. The opt-in Maven snapshot implementation in [MavenPreconditionInventory.java](../../dependency-elider-maven-plugin/src/main/java/io/github/spockz/elider/plugin/MavenPreconditionInventory.java) captures declared source, output, and resource providers and revalidates root membership and digests; [ADR0008MavenPreconditionInventoryTest.java](../../dependency-elider-maven-plugin/src/test/java/io/github/spockz/elider/plugin/ADR0008MavenPreconditionInventoryTest.java) covers source/output/resource providers, generated-name limitations, unknown filesystem entries, strict artifact failures, and snapshot mutation. [ADR0008MavenPreconditionPublicationTest.java](../../dependency-elider-maven-plugin/src/test/java/io/github/spockz/elider/plugin/ADR0008MavenPreconditionPublicationTest.java) covers shared-snapshot publication, output drift, stale-output ownership, and transactional rollback.

Core CycloneDX and OpenVEX serializers support the precondition attestation. [ADR0008PreconditionVexSerializationTest.java](../../elider-core/src/test/java/io/github/spockz/elider/metadata/ADR0008PreconditionVexSerializationTest.java) is Surefire-selectable and checks both schemas, exact post-inventory component and digest binding, omitted-code precedence, and order-independent conflict rejection. Maven publication revalidates the complete provider inventory before replacing outputs; the serializers independently rehash the affected component file.

Typed advisory ingestion and refresh are implemented in [AdvisoryEvidenceReader.java](../../elider-core/src/main/java/io/github/spockz/elider/scanner/AdvisoryEvidenceReader.java), [AdvisoryEvidenceWriter.java](../../elider-core/src/main/java/io/github/spockz/elider/scanner/AdvisoryEvidenceWriter.java), [OsvSnapshotIndexer.java](../../elider-core/src/main/java/io/github/spockz/elider/scanner/OsvSnapshotIndexer.java), and [VulnerabilityCacheManager.java](../../elider-core/src/main/java/io/github/spockz/elider/scanner/VulnerabilityCacheManager.java). Their focused tests cover strict v1 documents, OSV record ownership, multiple CNA products, package-only retention, separate origins, unresolved structured candidates, invalid-cache online/offline behavior, full-snapshot withdrawal, and publication failure preservation.

## Decision requested

Determine whether optional scanner orchestration provides enough reproducibility and workflow value to justify its compute, network/database, and failure-policy costs. Keep package-level comparison and evidence-backed VEX generation as separate capabilities.
