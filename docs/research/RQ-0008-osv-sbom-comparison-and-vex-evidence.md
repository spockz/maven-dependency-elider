# RQ-0008: OSV SBOM Comparison and VEX Evidence

## Status

Open

## Current boundary

The Maven plugin emits a post-elision CycloneDX SBOM when configured trimming runs. The core provides strict vulnerability-symbol mapping parsing/merging, explicit-source cache refresh with offline fallback, and a fail-closed omitted-code proof. Maven assessment connects omitted-code evidence to CycloneDX and OpenVEX output when a high-confidence mapping matches a retained trimmed component and archive inspection proves all mapped classes and nested classes absent. The core also carries exact prerequisite-class metadata and a digest-bound complete-inventory proof model under [ADR-0008](../adr/0008-precondition-gated-vex-attestations.md). Core CycloneDX and OpenVEX serializers support both evidence types. Maven snapshot-aware assessment emits precondition evidence and the distinct inactive-precondition report category only when a complete opted-in inventory proves the exact prerequisite coordinate and class absent for the exact affected version. Applicable mappings are resolved after POM precedence, then grouped by CVE and scope-free exact component identity. Every applicable mapping must agree on confidence, vulnerable classes, prerequisite coordinate, and prerequisite class; conflicting metadata suppresses VEX evidence and report classifications for that group. Equivalent overlapping ranges produce at most one statement. Omitted-code evidence takes precedence only after this conflict check; a successful precondition proof suppresses a contradictory conservative-omission report. The Maven goal captures and revalidates the inventory before publication. The Maven publication layer shares that snapshot with assessment and serializers and installs reports, SBOMs, VEX, Maven views, and resolver-plan updates through a rollback transaction. The serializers resolve the exact retained component and rehash its affected file; the publisher also checks the full inventory fingerprint and provider digests. The accepted claim does not extend beyond the declared Maven inventory. OSV-Scanner can match package coordinates from CycloneDX SBOMs against its vulnerability data ([official SBOM scanning usage](https://google.github.io/osv-scanner/usage/scan-source)); that package-level result does not identify which class or method a CVE affects.

## Track 3 evidence status

The external `make scan-sbom` harness compares machine-readable OSV-Scanner results for the example's baseline and post-elision CycloneDX inventories. It records a common scanner executable/version, separate start and completion timestamps for each scan, the SHA-256 of each input SBOM, the raw scan JSON, and the package-level delta. Each SBOM is hashed before and after its scan; a changed file aborts comparison, and classification uses the in-memory inventory parsed from the bytes whose hash is recorded. It requests offline vulnerability matching so both scans use the scanner's shared local cache. OSV-Scanner does not expose a database revision in this workflow, so identical database contents are not claimed or independently verified. The harness accepts exit status `1` only when valid JSON contains findings and accepts status `0` only when JSON has no findings; inconsistent output, other nonzero statuses, malformed JSON, and status `1` without findings are execution/result errors. A finding is called eliminated only if the associated component is absent from the post-elision SBOM; if that component remains but the finding is not returned, the report labels it separately. Older OSV-Scanner output without PURLs is resolved against the input inventory by Maven coordinate and version; if multiple PURL variants match, the finding remains unclassified.

An eliminated finding means that the baseline package finding did not match a package finding in the post-elision inventory. It is not evidence that vulnerable code was removed or that a product is unaffected, and the harness emits no VEX. This resolves the decoupled CI workflow question in favor of an external comparison gate while leaving VEX eligibility subject to the separate symbol-evidence gates below.

## Research questions

1. Should the plugin optionally invoke OSV-Scanner against both a baseline SBOM and the post-elision SBOM, or should scanning remain an external CI step?
2. If it is integrated, how should scanner version, vulnerability database revision/time, target inventory, and outputs be recorded so pre/post results are comparable and reproducible?
3. Can the difference be reported only as findings no longer matched to the post-elision component inventory, without implying exploitability or code-level remediation?
4. What should happen when the scanner, network, or vulnerability database is unavailable: skip explicitly, warn, or fail? How can offline use remain clear and auditable?
5. Is there reliable vulnerability data that maps a CVE to specific classes or members, and can that map be linked to verified trim output strongly enough to support `code_not_present` VEX? (Resolved by [ADR-0006](../adr/0006-dual-source-vulnerability-advisory-ingestion-from-cvelist-v5-and-osv-maven.md); the existing omitted-code path uses OSV Maven and CVEList v5 evidence.)
6. How should advisories mapping multiple vulnerable classes be interpreted across wide version ranges? For instance, Jackson Core `CVE-2026-68494` maps both `ByteArrayFeeder` and `StreamConstraintsException`, but `StreamConstraintsException` only exists in versions >= 2.15 while versions < 2.15 are also marked vulnerable. Does the presence of any mapped class indicate vulnerability, or must all be present? Under what conditions can current fail-closed strictness be relaxed?

## Options

1. Keep scanner execution external. Users scan the generated SBOM or final package in their CI security stage and retain scanner-owned results.
2. Add opt-in plugin orchestration for pinned scanner versions and explicit pre/post inventories, but emit package-level finding deltas only.
3. Add VEX generation only when a vulnerability-to-code mapping and verified evidence support the chosen VEX status and justification. Omitted-code and precondition proof, assessment, serialization, and transactional Maven publication are implemented.

## Benefits and costs

Integration could make the tested post-elision inventory easier to assess and could show which package findings no longer match that inventory. It adds scanner startup time, network/database access or database maintenance, version and database drift, output storage, and policy for failures and offline builds. A changed or missing package finding is only an inventory delta; it does not prove that vulnerable code was removed or that the product is unaffected.

## Evidence gates

- Compare scans of explicitly identified baseline and post-elision CycloneDX inventories using the same scanner version and a recorded database revision or timestamp.
- Label results as package-level findings; do not infer class-level status from an absent package finding or an elision decision.
- Generate omitted-code VEX only when vulnerability data maps the CVE to code with sufficient precision and verified trim evidence establishes that mapped code is absent from the final component. A separate precondition proof may generate VEX for a retained affected component only when its mapping identifies both the required Maven coordinate and exact fully qualified prerequisite class, and both are absent from the complete declared inventory. Require explicit `elide.preconditionClassPathComplete=true` opt-in. The captured inventory must include declared application classes/resources and every effective post-elision dependency archive, with an inventory fingerprint and per-file digests revalidated during proof. Unknown or unreadable inputs, incomplete source/resource discovery, the class in any inventoried provider, a digest mismatch, or an ambiguous mapping suppresses the statement. This proves absence only within the declared Maven inventory; providers introduced later by packaging or deployment remain outside the claim. Scanner findings alone must produce no VEX statement.
- Test positive and fail-closed cases for both proof kinds, including version-level findings that remain after trimming, coordinate-only mappings, equivalent classes in other dependencies or application providers, incomplete inventories, and digest mutation.
- Core omitted-code proof requires exact group, artifact, version, type, and classifier identity, HIGH mapping confidence, matching archive digests, mapped classes present in the original, and mapped plus original nested classes absent from the trimmed archive. Scope is ignored for package identity. Maven assessment applies `versionRangeSpec` before attempting proof.
- Strict JSON input rejects unknown/duplicate fields and trailing documents. Cache refresh validates configured HTTP(S) URIs, uses bounded lock/body waits, streamed temporary files, atomic replacement, and cache/seed fallback. The Maven goal defaults to OSV Maven snapshot and CVEList v5 URIs and refreshes missing or stale cache content unless Maven is offline. Explicit POM mappings remain supported and override cached entries; the bundled seed is empty.
- Core mapping metadata, the complete-inventory proof model, serializers, Maven snapshot-aware assessment, and transactional goal publication are implemented. The assessment rejects conflicting applicable evidence before proof selection, coalesces equivalent overlapping mappings, normalizes identity without Maven scope, and keeps conservative omission and inactive classifications mutually exclusive. The goal requires the explicit completeness opt-in, captures the inventory after planning, and aborts publication if revalidation finds changed provider membership or content. Scanner orchestration remains separate. The core proof requires a caller-supplied complete inventory and does not prove absence of providers introduced outside the declared Maven build inventory; serializers recheck the exact affected component path and file digest.

## Implemented evidence and architectural alignment

The proof API is constrained by the per-JAR provenance and original-artifact immutability invariants in [ADR-0003, Invariants](../adr/0003-proguard-core-intra-jar-trimming-and-cyclonedx-pedigree.md#invariants). [OmittedCodeProof.java](../../elider-core/src/main/java/io/github/spockz/elider/model/OmittedCodeProof.java) verifies exact artifact identity and recorded digests before and after inspecting each archive; [OmittedCodeProofTest.java](../../elider-core/src/test/java/io/github/spockz/elider/model/OmittedCodeProofTest.java) covers successful proof, surviving mapped and nested classes, digest mutation, identity mismatch, and a mapped class absent from the original.

The core precondition model is implemented in [PreconditionClassInventory.java](../../elider-core/src/main/java/io/github/spockz/elider/model/PreconditionClassInventory.java) and [PreconditionProof.java](../../elider-core/src/main/java/io/github/spockz/elider/model/PreconditionProof.java). [ADR0008PreconditionProofTest.java](../../elider-core/src/test/java/io/github/spockz/elider/model/ADR0008PreconditionProofTest.java) covers exact-class absence, dependency and application providers, source-name/digest binding, incomplete inventories, mutation, and malformed inputs. [MavenVulnerabilityAssessment.java](../../dependency-elider-maven-plugin/src/main/java/io/github/spockz/elider/plugin/MavenVulnerabilityAssessment.java) applies complete-inventory proofs to exact retained candidates and classifies only successful proofs as inactive; [ADR0008MavenPreconditionAssessmentTest.java](../../dependency-elider-maven-plugin/src/test/java/io/github/spockz/elider/plugin/ADR0008MavenPreconditionAssessmentTest.java) is Surefire-selectable and covers exact version selection, overlapping mapping order/conflicts, confidence and incomplete metadata, POM overrides, scope-free precedence, opt-out diagnostics, report category separation, and conservative-omission reconciliation. The opt-in Maven snapshot implementation in [MavenPreconditionInventory.java](../../dependency-elider-maven-plugin/src/main/java/io/github/spockz/elider/plugin/MavenPreconditionInventory.java) captures declared source, output, and resource providers and revalidates root membership and digests; [ADR0008MavenPreconditionInventoryTest.java](../../dependency-elider-maven-plugin/src/test/java/io/github/spockz/elider/plugin/ADR0008MavenPreconditionInventoryTest.java) covers source/output/resource providers, generated-name limitations, unknown filesystem entries, strict artifact failures, and snapshot mutation. [ADR0008MavenPreconditionPublicationTest.java](../../dependency-elider-maven-plugin/src/test/java/io/github/spockz/elider/plugin/ADR0008MavenPreconditionPublicationTest.java) covers shared-snapshot publication, output drift, stale-output ownership, and transactional rollback.

Core CycloneDX and OpenVEX serializers support the precondition attestation. [ADR0008PreconditionVexSerializationTest.java](../../elider-core/src/test/java/io/github/spockz/elider/metadata/ADR0008PreconditionVexSerializationTest.java) is Surefire-selectable and checks both schemas, exact post-inventory component and digest binding, omitted-code precedence, and order-independent conflict rejection. Maven publication revalidates the complete provider inventory before replacing outputs; the serializers independently rehash the affected component file.

Mapping ingestion and refresh are implemented in [VulnerabilityMappingReader.java](../../elider-core/src/main/java/io/github/spockz/elider/scanner/VulnerabilityMappingReader.java), [VulnerabilityMappingWriter.java](../../elider-core/src/main/java/io/github/spockz/elider/scanner/VulnerabilityMappingWriter.java), and [VulnerabilityCacheManager.java](../../elider-core/src/main/java/io/github/spockz/elider/scanner/VulnerabilityCacheManager.java). Their tests are [VulnerabilityMappingReaderTest.java](../../elider-core/src/test/java/io/github/spockz/elider/scanner/VulnerabilityMappingReaderTest.java) and [VulnerabilityCacheManagerTest.java](../../elider-core/src/test/java/io/github/spockz/elider/scanner/VulnerabilityCacheManagerTest.java); these cover strict JSON, v1 `requiresClass` round-trip, override precedence, offline/cache fallback, bounded refresh, temporary-file cleanup, and replacement of an existing longer temporary file.

## Decision requested

Determine whether optional scanner orchestration provides enough reproducibility and workflow value to justify its compute, network/database, and failure-policy costs. Keep package-level comparison and evidence-backed VEX generation as separate capabilities.
