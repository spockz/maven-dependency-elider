## Agreed scope

At the existing invocation-driven refresh, inspect the Maven ZIP object's `Last-Modified` with HEAD and decide whether to download the full ZIP. Rebuild from `Maven/all.zip` when source metadata is absent/incompatible, the source timestamp differs, the advertised ZIP timestamp is at least 24 hours old, or force sync is requested. Otherwise reuse the current snapshot. On every due synchronization, reconcile the complete `Maven/modified_id.csv` by OSV record ID. Retain each source record's `modified` timestamp and replace that ID's entire record and derived Maven associations. Publish snapshot changes, delta results, and metadata together, or preserve the preceding committed state.

Keep the default 24-hour TTL, configured TTL override, force-sync option, explicit update goal, and Maven offline behavior. This is not a background scheduler or a delta-only optimization. It does not reopen complete source-to-binary attribution, broad affected-version semantics, external scanner orchestration, or ADR-0008's inventory proof.

The user's approved amendment requires `zipLastModified` from snapshot HTTP response metadata and `lastSyncTimestamp` from local successful synchronization time. Reusing snapshot bytes must not invent a new source timestamp. The local 24-hour TTL controls when synchronization is due; source ZIP age, timestamp changes, metadata validity, and force determine whether ZIP bytes are fetched. Architectural approval and documentation changes are not implementation evidence.

## Timestamp and cadence contract

| Value | Meaning | Required source and use |
| :--- | :--- | :--- |
| `zipLastModified` | Modification time advertised for the downloaded ZIP object, not a shared export watermark. | Parse the `Last-Modified` metadata on the successful response carrying those ZIP bytes. Missing or malformed metadata fails the refresh; never substitute local time or file mtime. |
| Record `modified` | Upstream revision timestamp for one OSV advisory. | Preserve and validate the source value for snapshot and fetched records. Compare revisions within the same OSV ID. |
| CSV row timestamp | Exported revision claim for its OSV ID. | Parse the complete CSV; use it to select record fetches, without assuming row order or treating absence as deletion. |
| `lastSyncTimestamp` | Local successful synchronization/publication time. | Capture local time after staging and validation, and publish it only if the entire transaction commits. Use it for the next invocation's TTL decision, never as upstream coverage evidence. |

An unchanged old `zipLastModified` may accompany a successful delta synchronization with a new `lastSyncTimestamp`. An advertised ZIP timestamp at least 24 hours old causes a full ZIP fetch on each due sync; force sync also fetches the ZIP even when the remote timestamp is unchanged and recent. Failure changes neither timestamp. Missing or incompatible local metadata is a cache miss requiring online reconstruction or the existing offline conservative fallback, not an opportunity to infer source time from local file timestamps.

## Reconciliation and refusal rules

1. When a full download is required, build a new staging index from the ZIP rather than overlaying the previous cache. Preserve distinct OSV IDs even when they share CVE aliases or Maven coordinates. Retain source timestamps, aliases, package contexts, and separate derived evidence origins. When ZIP reuse is allowed, start from the fully validated compatible cached owner index.
2. Read the entire modified-ID export. Normalize duplicate rows for one ID to the greatest valid timestamp; process independently of row order. Malformed rows, invalid timestamps or unsafe IDs fail the attempt explicitly. The accepted policy must not silently truncate the feed or report a failed request as an empty successful export.
3. Fetch an ID absent from the staged snapshot, or an ID whose CSV revision is newer than its staged record's `modified`. Do not use either `zipLastModified` or `lastSyncTimestamp` as a global cutoff. Validate the fetched ID and its source timestamp; a response older than the selected CSV revision cannot complete the attempt successfully.
4. Replace that ID's entire source record and rederive all Maven package, alias, CNA and candidate associations. Never merge or deduplicate by CVE plus coordinate, and never retain old associations removed by the replacement record. A fetched withdrawal or record with no Maven associations removes that ID's old Maven contribution.
5. Delta absence is not a deletion event. The next full snapshot rebuild reconciles records deleted upstream or moved out of Maven. A missing individual object or failed fetch is a failed attempt, not an implicit tombstone. Full snapshot replacement plus explicit withdrawal handling must not resurrect stale records from the prior cache.
6. Preserve bounded network/body/lock waits, strict record validation, producer compatibility and resource cleanup. Validate persisted records with the Maven consumer validator before CACHE admission or snapshot reuse. An invalid cached range forces online reconstruction; offline or failed reconstruction uses the typed seed with a diagnostic. Stage all results before publication. Any snapshot, CSV, selected-record, validation or publication failure leaves the old committed index and metadata intact; rollback failure is diagnosed and recovery evidence is retained, and a potentially mixed cache pair is not admitted.
7. Normal analysis may use the prior compatible cache with a diagnostic on refresh failure, or the existing typed seed/cache-miss fallback when no compatible cache exists. Offline execution performs no network calls and does not advance successful-sync metadata. The explicit update goal rejects offline execution and reports synchronization failure rather than claiming fallback data was updated.

## Consistency and limits

The ZIP, CSV and individual records are independently exported objects without a documented shared watermark. Their successful download does not prove that every upstream change through local `lastSyncTimestamp` is represented. Per-record `modified` comparisons prevent revision regression for selected IDs but do not establish global completeness or detect deletions absent from the CSV.

The intended local update opportunity is the configured refresh interval, 24 hours by default, followed by the next eligible plugin invocation. Source ZIP age may force a full download on a due sync even when its timestamp has not changed. Upstream export delay, races between objects, deletions awaiting a later full ZIP, network failures, offline builds and the absence of a later invocation can extend visibility delay. This is eventual consistency, not a zero-lag promise or a hard maximum freshness guarantee. No daily task runs when Maven is not invoked.

## Implementation and verification evidence

The implementation stages and validates the complete snapshot when required, response-derived ZIP `Last-Modified`, complete modified-ID export and selected source records before transactional publication. `OsvAdvisoryRecord.modified` is preserved by the strict v1 document codec. Delta replacement is keyed by OSV record ID; the full snapshot remains authoritative for records absent from Maven, and explicit withdrawals remove only their owner. If rollback leaves recovery backups, cache admission stays seed-only offline and forces a full online rebuild; retries use distinct backup paths so the original recovery bytes survive. A successful recovery removes the retained artifacts. Existing producer compatibility, offline behavior and typed proof boundaries remain in place.
