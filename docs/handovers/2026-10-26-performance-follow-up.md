## Performance evidence and interpretation

The sampled `TreeMap.getEntry` calls are in the JDK collection backing ProGuard's `ClassPool.getClass`. ProGuard owns that lookup implementation; ProGuard's reference initializers and our graph-building path determine how many lookups are requested. Slice 2.6c adds a context-local hash lookup in our frozen graph pool while preserving ProGuard class objects and sorted traversal. The hot leaf is in the ProGuard/JDK lookup path, while the call volume is shared across the analysis pipeline. The sample share is not a predicted end-to-end speedup.

Three matched unprofiled post-7.6 cycles all passed the four example fixtures. Basic baseline times were 2.247–2.285 s (median 2.262 s), and elision times were 4.214–4.258 s (median 4.224 s); overheads were +1.929–+1.996 s (median +1.977 s). Spring baseline times were 4.086–4.128 s (median 4.106 s), and elision times were 24.508–24.553 s (median 24.523 s); overheads were +20.380–+20.467 s (median +20.417 s). Compared with the earlier 6.6 checkpoint, these medians are close (+1.972 s and +20.337 s), but multiple code slices and environment state differ, so this does not isolate one change's effect. These cycles ran on the 79-JMOD fallback path. The final removal of redundant JMOD central-directory preflight changed fresh JMH by about 3 ms/op (96.488 to 93.465 ms/op), small beside the cycle timing ranges; the examples were not repeated. The 7.5 byte arrays added 130,382,660 bytes per request context.

The production JMH operation calls `MavenDependencyTrimmer.trim` for one tiny candidate, including dynamic roots, dependency digests, cache-manifest validation, and cached-output hashing. With GraalVM JDK 21.0.12+7.1 and JMH 1.37, two forks, three 1 s warmups, and five 1 s measurements, the warmed request/cache hit measured **0.093 ±0.001 ms/op** (range 0.093–0.094). A separate fresh request/cache hit measured **93.465 ±0.391 ms/op** (range 92.999–94.012), about 9.3× above the <10 ms fast-path budget. It captures identity for a new operation context, not a Maven invocation; the warmed result represents repeated calls after the invocation-owned platform identity is available. For this JDK, the identity covers 81 sources (ct.sym, release metadata, and 79 JMODs) and retains zero archive byte arrays. Serialized identity length is 17,805 characters, including 14,336 path-plus-digest characters; these counts do not estimate exact heap usage.

Separate JFR runs used one fork, one 1 s warmup, and two 2 s measurements. Fresh measured 94.377 ms/op with 44 execution samples; SHA-256 compression, `ZipFile$Source.checkAndAddEntry`, and `ZipEntryIterator.next` each had six samples. The 79-JMOD preflight was removed; ZIP samples now cover selected archive inspection and operation work. Allocation samples were weighted toward ZIP iteration (16.73%), ASM reads (12.12%), and digest setup (11.18%). Warm measured 0.096 ms/op with 38 execution samples and no direct `jdk.FileRead` events. JFR includes setup/warmup and uses sampled execution/allocation, so the figures are not exact total CPU or allocation. A separate unprofiled Spring elision Maven process selected the Maven Launcher PID by command line (PID 835033); `/proc/<pid>/status` `VmHWM` sampled every 50 ms for 485 samples gave a **3,119,312 KiB** peak. Child processes were excluded. The earlier multi-PID aggregate was discarded. This is about 13 MiB above 7.5's single-process 3,106,188 KiB reading and within run variability; no RSS improvement is claimed. Fresh-context latency remains above the <10 ms target despite warmed same-request reuse meeting it. Slice 7.7 will measure whether bounded parallel platform hashing materially improves fresh-context time without harming reactor throughput.

## Decision: input stability during a Maven invocation

Resolved input files are assumed stable during one Maven invocation. Compute each content digest needed for the cache identity, but do not repeat full input hashing at publication solely to defend against concurrent edits. Such edits already make a Maven build nondeterministic. Continue staging cache outputs and atomically publishing complete outputs so a failed write cannot leave a partial result.

The ADR records this decision in `docs/adr/0004-assume-resolved-inputs-stable-during-build.md`.
