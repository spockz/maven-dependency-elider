## Performance evidence and interpretation

The sampled `TreeMap.getEntry` calls occur in ProGuard `ClassPool.getClass`; our graph-building path and ProGuard's reference initializers determine how often those calls occur. The frozen index in 2.6c changes lookup service while preserving the pool's class objects and sorted storage. The reported sample share is not a predicted end-to-end speedup.

Three matched unprofiled post-7.5 cycles all passed the four example fixtures. Basic baseline times were 2.267–2.269 s (median 2.269 s), and elision times were 5.605–5.626 s (median 5.611 s); overheads were +3.336–+3.359 s (median +3.342 s). Spring baseline times were 4.100–4.160 s (median 4.125 s), and elision times were 25.858–26.085 s (median 26.037 s); overheads were +21.758–+21.925 s (median +21.912 s). The earlier 6.6 checkpoint measured median overheads of +1.972 s and +20.337 s respectively. Several code slices and environment state differ, so this comparison does not isolate 7.5's effect. The fresh-request JMH operation below measures the additional first-capture cost separately from a warmed request hit; representative one-project Maven builds include that first-capture path and remain slower than the 6.6 checkpoint.

The warm-request JMH operation still calls production `MavenDependencyTrimmer.trim` for one tiny candidate, including dynamic roots, dependency digests, cache-manifest validation, and cached-output hashing. It measures 0.094 ±0.001 ms/op with a request-owned platform snapshot and is below the <10 ms repeated-request target. A separate fresh-request operation, which recaptures the JDK platform inputs, measures 1,172.372 ±12.433 ms/op; this is capture cost for a new operation context, not a Maven invocation and not subject to the warmed-hit target. For GraalVM 21, one captured context retains 130,382,660 bytes of selected `ct.sym`, release metadata, and ordered JMOD content (about 124.3 MiB). A focused unprofiled Spring elision Maven process peaked at 3,106,188 KiB RSS (about 2.96 GiB); this includes the whole process and must not be added to the retained-byte figure.

JMH JFR runs were separate from timing runs. The fresh operation profile had 50 execution samples: SHA-256 compression appeared in 27 (54%) and SHA-1 in 20 (40%); allocation samples were dominated by file reads. The warmed profile had 18 execution samples and recorded no `ct.sym` or JMOD reads. The separate Spring elision JFR covered 26.0 seconds and had 1,066 execution samples: ProGuard descriptor enumeration methods accounted for 14.45% and 12.38%, immutable map probing for 12.48%, and TreeMap lookup for 2.35%. Sampled allocation pressure was led by `String.substring` (24.74%); one `java.base.jmod` read accounted for 44.4 MB. These are sampled profiles, not exact total CPU or allocation accounting. The 6.7 warm-cache result remains above its <10 ms target and has different per-op semantics; do not compare it directly with the new warm-request operation.

## Decision: input stability during a Maven invocation

Resolved input files are assumed stable during one Maven invocation. Compute each content digest needed for the cache identity, but do not repeat full input hashing at publication solely to defend against concurrent edits. Such edits already make a Maven build nondeterministic. Continue staging cache outputs and atomically publishing complete outputs so a failed write cannot leave a partial result.

The ADR records this decision in `docs/adr/0004-assume-resolved-inputs-stable-during-build.md`.
