# ADR-0016: Test Compilation and Isolated Test Runtime Views

* **Status**: Proposed
* **Date**: 2026-11-21
* **Related**: [ADR-0002](0002-in-memory-artifact-mutation-for-downstream-packaging-transparency.md), [ADR-0003](0003-proguard-core-intra-jar-trimming-and-cyclonedx-pedigree.md), [ADR-0010](0010-process-classes-lifecycle-and-bytecode-completeness.md), [ADR-0012](0012-dual-layer-ban-policy-and-retention-naming.md), [ADR-0015](0015-forbidden-code-policy-and-evidence-bounded-cve-assessment.md), [RQ-0006](../research/RQ-0006-maven-artifact-view-consistency-and-early-resolution-hooks.md), [RQ-0017](../research/RQ-0017-source-generation-lifecycle-integration-and-deferred-source-root-completeness.md).

## Context

Elider executes at `process-classes`, after production compilation and before test compilation. It trims retained JARs and removes unused artifacts based on production roots, then changes the project artifact paths and publishes a resolver projection. A test can refer to a builder, fixture or whole dependency unused by production. The test compiler then sees the production result and can fail before tests run. [RQ-0017](../research/RQ-0017-source-generation-lifecycle-integration-and-deferred-source-root-completeness.md) documented this problem, but retaining test-only code in production output is not the desired solution.

The mediated Maven `TEST` dependency tree already reported by Elider is an artifact dependency graph, not a test-bytecode usage graph. Test classes do not exist until after `test-compile`; a clean build cannot derive their usage at `process-classes`.

## Decision

Keep production elision at `process-classes`. Preserve the **original, post-Maven-mediation and post-ban-policy** test inputs, including original paths for JARs that production elision trims or removes. Compile test sources against that original test compilation view. At `process-test-classes`, use the existing production reachability and dynamic-root analysis on compiled test output and the appropriate original test inputs to compute test requirements. Materialize the additional dependency code and resources in temporary test-only JARs, and run tests against the effective production view, ordinary test-scoped dependencies and those additions. The original production output, effective production dependencies, graph projection, packaged outputs, production SBOM and VEX remain based solely on the production analysis.

The test-only JARs are a preferred implementation for ordinary classpath builds, not a claim that splitting every JAR is safe. When a complete and correct overlay cannot be established, use a reported conservative **test-only** fallback, such as a test-specific complete artifact replacement, if it preserves class and resource semantics. If neither an overlay nor a safe fallback can be established, fail the affected test preparation with an actionable diagnostic; never change production output or report an incomplete overlay as complete. Preserve existing explicit exclusions, bans and forbidden-code enforcement: an audit-only original, excluded artifact or banned dependency must not be restored as a test input. Existing forbidden-code production scope remains unchanged; this ADR does not create a new test-scope policy exemption or silently enforce new ones.

The complete test-graph and automatic additions feature remains planned. The first slice is an opt-in Maven 3 lifecycle integration that accepts a caller-supplied additions JAR; its verified boundary is recorded below. Automatic lifecycle integration remains the goal for supported `process-classes` builds. Direct goals are verified only after Elider has run in the same invocation.

### Three distinct views

| Consumer | Required view | Boundary |
| :--- | :--- | :--- |
| Production analysis and packaging | Effective elided artifacts, trimmed files and production graph projection | Remains the authoritative live production and resolver view; never includes test additions. |
| Test compilation | Original effective Maven test compilation inputs, including production dependencies before elision and ordinary test dependencies | Must be ready before the compiler Mojo is configured. It must respect Maven mediation, scopes, reactor paths and already applied bans. |
| Test execution | Effective production view plus ordinary test dependencies and the computed test-only additions | Test-only changes are visible to the test runner, not to packaging or later production resolution. |

Maven's test classpath normally contains test dependencies as well as production code; those dependencies, including the test-only additions, can supply classes during tests that are absent from deployment. This is a consequence of testing with a test classpath, not a new claim that ordinary Maven tests prove production completeness. State which additions were used, and recommend a packaged-application test with an isolated production classpath when stronger deployment confidence is wanted.

### Maven integration: findings and implementation gate

* In Maven 3, [`MavenProject.getTestClasspathElements()`](https://maven.apache.org/ref/3.9.9/maven-core/xref/org/apache/maven/project/MavenProject.html) builds its list from the project's artifact view, and [compiler 3.13's `TestCompilerMojo`](https://maven.apache.org/plugins-archives/maven-compiler-plugin-3.13.0/xref/org/apache/maven/plugin/compiler/TestCompilerMojo.html) injects it as `testPath`. Compiler settings, generated test roots, annotation processors, toolchains, paths and module-path decisions remain owned by the user's compiler execution.
* [`MavenArtifactViewUpdater`](../../dependency-elider-maven-plugin/src/main/java/io/github/spockz/elider/plugin/MavenArtifactViewUpdater.java) matches artifact identity without scope and replaces file pointers in multiple artifact views. `MavenElisionOutputPublisher` publishes the resulting project artifact sets; `ResolverArtifactPlanPublisher` and `EliderRepositorySessionDecorator` also apply production replacements to later resolver requests. Maven 3.9.9's [`DefaultArtifact.equals` and `hashCode`](https://maven.apache.org/ref/3.9.9/xref/org/apache/maven/artifact/DefaultArtifact.html) ignore scope and file path, so two default artifacts with identical coordinates cannot coexist merely by changing scope in a `Set`. A duplicate dependency declaration is not a reliable independent original file view, and changes to only `project.getArtifacts()` do not establish resolver isolation.
* Maven 3.9.9's [`DefaultBuildPluginManager`](https://maven.apache.org/ref/3.9.9/maven-core/xref/org/apache/maven/plugin/DefaultBuildPluginManager.html) configures the Mojo **before** `MojoExecutionListener.beforeMojoExecution`. Therefore switching the project view only in that callback is too late for the compiler's injected test path. Its failure callback does not cover ordinary checked Mojo execution or compilation failures, so do not rely on it alone for restoration. The [listener API](https://maven.apache.org/ref/3.9.9/maven-core/apidocs/org/apache/maven/execution/MojoExecutionListener.html) is documented as work in progress; its availability and timing are not a universal Maven compatibility promise.
* In Maven 3.9.9's [`MojoExecutor`](https://maven.apache.org/ref/3.9.9/maven-core/xref/org/apache/maven/lifecycle/internal/MojoExecutor.html), dependency resolution precedes the `MojoStarted` execution event; that event precedes Mojo configuration and execution, with `MojoSucceeded` or `MojoFailed` fired for the handled success and checked-failure paths. A chained Maven execution listener is a candidate for a narrowly scoped compiler-view switch and restoration, but must be proven registered before execution, correctly chained with existing listeners, and effective despite earlier resolver decisions. Its behavior for unchecked failures, process interruption and other Maven versions needs separate verification. Maven's [`EventSpyDispatcher`](https://maven.apache.org/ref/3.9.9/maven-core/xref/org/apache/maven/eventspy/internal/EventSpyDispatcher.html) catches and logs callback exceptions, so an `EventSpy` callback alone cannot enforce fail-closed restoration or delivery.
* [Surefire `additionalClasspathElements`](https://maven.apache.org/surefire/maven-surefire-plugin/examples/configuring-classpath.html) adds paths at the end of the test **runtime** classpath and does not change test compilation. It is a candidate for test-only overlay delivery, not a solution for the compiler. Appending a JAR cannot override earlier duplicate classes or resource-selection rules. Do not use `additionalClasspathDependencies` as a shortcut for preserving the project's mediated graph: its documented resolution does not use project dependency management or resolve conflicts with project dependencies.
* Maven 3.9.9's [execution-plan calculator](https://maven.apache.org/ref/3.9.9/maven-core/xref/org/apache/maven/lifecycle/internal/DefaultLifecycleExecutionPlanCalculator.html) finalizes per-Mojo execution configuration when constructing the plan. Changing only the project plugin model during `process-test-classes` may therefore be too late to affect the pending Surefire execution. Prototype merging generated overlay paths into the selected `MojoExecution` before `getConfiguredMojo`, or an earlier-declared property whose evaluation at Mojo configuration has been proven late enough. Preserve plugin-level and execution-level entries and test two distinct Surefire executions; do not claim delivery merely because a project property or plugin model changed.

**Local experiment, 2026-11-21:** A test-only core extension chained the existing execution listener in `afterSessionStart`. For one Maven 3.9.11 app it switched the project's single library path to the original on `mojoStarted(testCompile)`, restored the trimmed path on `mojoSucceeded` or `mojoFailed`, and added a hand-built overlay to the actual Surefire `MojoExecution` on `mojoStarted(test)`. The baseline without the compiler switch failed to compile `Builder`; without the overlay compilation succeeded but Surefire failed with `NoClassDefFoundError`. With both switches, one JUnit test passed, checking that `Client` loaded from `trimmed.jar` and `Builder` from `overlay.jar`; Shade bundled only the production `App` and `Client` classes. A deliberate compiler failure logged restoration. A later dependency-plugin classpath contained the trimmed path. [RQ-0017](../research/RQ-0017-source-generation-lifecycle-integration-and-deferred-source-root-completeness.md#11-local-maven-view-experiment-2026-11-21) records the fixture, commands, outcomes and limits.

This is evidence for a specific integration direction, not completion of the gate. The extension simulated trimming with prebuilt JARs; it did not run Elider, build a test graph, publish Elider's resolver plan, or establish that an independent fresh resolver request sees the production projection. It did not test multiple compiler/runner executions, user Surefire entries, direct or partial goals, reactor, JPMS, skipped tests, dropped artifacts, policy bans, dynamic roots or interruption. Verify those cases before treating the mechanism as supported. Do not adopt the experimental Java reflection proxy as production design merely because it worked in this fixture.

**Real-Elider first-slice proof, 2026-11-21:** The packaged plugin and core extension now run in a focused `DependencyContextLifecycleIT` fixture with Maven 3.9.11, Compiler 3.13.0, Surefire 3.5.2 and Shade 3.6.0. Production `App` uses `Client`; Elider retains `Client`, removes `Builder`, `Helper` and `Unused` from that JAR, and drops a separate compile-scoped `test-only-library` used only by the test. Without the test-view listener, `testCompile` fails for `Builder` and `Marker`. A **test-only extension**, installed alongside the real core extension, proves the `afterSessionStart` execution-listener candidate: it chains the preexisting listener; captures the fixture's original artifact objects and files on `MojoStarted(elide)`; switches them on `MojoStarted(testCompile)` before compiler configuration; and restores the production set and paths on `MojoSucceeded` or `MojoFailed`. `MojoStarted(surefire:test)` appends a hand-built additions JAR to that execution while preserving an existing user classpath entry. No production plugin hook or automatic overlay is installed by this proof.

The passing test observes `Client` from the trimmed JAR and `Builder` and `Marker` from the additions JAR. Omitting the additions JAR fails at runtime for `Builder`; omitting only `Helper` fails for `Helper`. After tests, `PostElideProbeMojo` makes a distinct `ProjectDependenciesResolver.resolve` request with the live session. A scoped request marker lets a test-only decorator observer identify that request and see `EliderRepositorySessionDecorator$PlannedWorkspaceReader`; its compile-filtered resolved list contains exactly the trimmed retained JAR path and digest. Maven's raw dependency graph still contains declared JUnit test nodes despite the compile filter, so the graph and filtered result are asserted separately. Shade then bundles `Client` but none of `Builder`, `Helper`, `Unused`, `Marker` or the additions JAR. The baseline, successful and failed compiler callbacks, no overlay, cached trim, partial `process-test-resources`, direct compiler/runner/probe goals, appended probe, `skipTests`, `maven.test.skip`, no test sources and a preexisting Surefire classpath element have been exercised in separate real Maven processes. [RQ-0017 §12](../research/RQ-0017-source-generation-lifecycle-integration-and-deferred-source-root-completeness.md#12-real-elider-first-slice-proof-2026-11-21) records commands and observed paths.

**Hook choice for the fixture:** the scoped execution-listener switch satisfies the tested lifecycle and packaging isolation boundary. It is a prototype, not a supported user feature. The prototype captures before Elider's ban application, so it cannot supply the required post-ban allowed inventory for production integration. The production handoff must publish an immutable allowed original view across realms without changing the resolver plan, and must fail closed for unsupported ordering. Multiple compiler/Surefire executions, a user execution listener beyond the observed Maven listener, unchecked callback failures, process interruption, Maven 4, reactor/module-path builds, annotation processors, policy bans, forbidden-code and precondition-proof configurations, SBOM/VEX comparison, test-report persistence and automatic test graph/overlay construction remain unverified. Direct goals are verified only when `process-classes` has run first in the same invocation. No test report or persistence format exists in this slice. Keep the proposed decision below distinct from this fixture evidence.

**Packaged first-slice integration, 2026-11-22:** The packaged Elider plugin and core extension now use a chained `ExecutionListener` installed by `EliderLifecycleParticipant.afterSessionStart`. `MojoStarted(elide)` captures the original mediated artifacts. Immediately before production publication, the plugin records their ordered identity, scope and paths in a JDK-only, version-1 session payload; the extension reads that payload after Elider succeeds. `MojoStarted(testCompile)` switches only the project artifact set and file pointers before compiler configuration and before forwarding the callback. `MojoSucceeded`, `MojoFailed`, project completion and session completion restore the production set and paths. A callback failure during the switch rolls back. The production resolver plan stays untouched. `MojoStarted(surefire:test)` appends a supplied additions JAR to that execution's `additionalClasspathElements`, preserving the existing entry. A separate test-only observer checked callback chaining, the original view at compiler start, and production restoration after successful and failed compilation. The real-Elider package, class-origin and fresh resolver checks above also pass against this production hook; [RQ-0017 §13](../research/RQ-0017-source-generation-lifecycle-integration-and-deferred-source-root-completeness.md#13-packaged-first-slice-integration-2026-11-22) records the command and outcomes.

**Surefire property correction, 2026-11-22:** An Astra review found that Maven 3.9.11's array converter chooses the `maven.test.additionalClasspath` parent value over child `additionalClasspathElement` entries. A real Maven package run with that user property compiled tests but failed at Surefire for missing `Builder` and `Marker`. The listener now appends the supplied additions path to the effective property value when present; with no property, it appends a child as before. The same run passes with both the user classpath resource and the additions JAR visible inside `AppTest`, while the production resolver and Shade assertions remain intact. One redundant clean package execution was removed after its assertions were consolidated into the fuller fixture run. [RQ-0017 §14](../research/RQ-0017-source-generation-lifecycle-integration-and-deferred-source-root-completeness.md#14-surefire-property-review-and-correction-2026-11-22) records the red and green commands and limits.

This slice requires the Elider core extension, one Maven project, a successful `elide` goal before `testCompile`, and `-Delide.testCompilationView=true`. `-Delide.testAdditionsJar=/absolute/path/additions.jar` is optional; when omitted, tests compile against originals but receive no extra runtime code. The caller builds that JAR; Elider does not analyze tests or generate it yet. The opt-in fails closed if banishment is requested, because the current pre-publication capture has not proven a post-ban allowed test inventory. It also fails for a missing or invalid supplied JAR, ambiguous original artifact identity, absent original files, a missing core extension, or direct test compilation without a successful Elide goal in the same invocation. No test report or persistence/replay format exists in this slice. Maven 3.9.11 with Compiler 3.13.0, Surefire 3.5.2 and Shade 3.6.0 is the verified combination; Maven 4, reactor projects, JPMS, other runners and plugin versions, multiple compiler/Surefire executions, unchecked Maven callback failure and process interruption remain unverified. Existing production ban, forbidden-code, SBOM and VEX code paths were not changed; their interaction with the opt-in view needs focused comparison before the full feature is supported.

**First implementation gate:** build a minimal real Maven lifecycle fixture to compare two integration candidates before committing to a hook:

1. A temporary original test compilation view activated **before compiler Mojo configuration** and restored immediately after `testCompile` on success or failure. Start with the experimentally viable Maven `MojoStarted`/`MojoSucceeded`/`MojoFailed` sequence and reproduce it with Elider's actual project and resolver plan; evaluate an earlier Elider lifecycle goal only if its wider exposure window can be closed safely. Protect invocations that end before `test-compile`, invoke other goals in between, run more than one test compiler execution, or invoke a compiler goal directly: no original production artifact may remain exposed to an unrelated packaging or resolver goal. Check listener registration, chaining, callback timing and failures on supported Maven versions rather than assuming them.
2. Distinct temporary test-scoped artifact entries or a compiler-specific classpath integration that makes original inputs available before injection without mutating the production resolver plan. Prove Maven identity, dependency mediation, original-versus-trimmed ordering, plugin-configuration merging, reactor artifacts and removal before test execution; do not assume a second declaration of the same coordinate works. Any synthetic entries must be isolated from POM, production SBOM, packaging and later project/resolver views.

Use the simpler candidate that meets the full acceptance contract. If neither is safe on a supported Maven configuration, report that configuration as unsupported and preserve the production view. The prototype must demonstrate a failed compilation with the current setup and a passing compilation with an actual test-only builder, then assert both effective project artifacts and a freshly resolved production tree and packaged bytes. It must cover `mvn test`, `mvn package`, `mvn process-test-resources`, direct compiler/test goals, an appended unrelated goal, and failure recovery. Do not implement a general phase-wide project swap without these checks.

For the supported standard lifecycle, bind or arrange test analysis after `test-compile` and before the test runner at `process-test-classes`. The extension may schedule the goal in the existing lifecycle participant, but must preserve explicit user executions and ordering. Package and resolver consumers retain or regain the verified production projection before they execute, even after compilation failure, skipped test compilation or repeated/direct goals. Test-only runner configuration must be scoped to the test execution, preserve user-supplied Surefire options and classpath entries, and not add dependency declarations to the project POM. Validate the mechanism under the project's supported Maven 3 configuration first; Maven 4, arbitrary test runners and integration-test plugins require separate verification and must not be silently claimed as supported.

### Test graph and additions

1. Capture immutable original mediated artifacts, their scope, order, paths and existing content identities before mutation; keep this operation-local and independent of the later production resolver replacement. Preserve the original project test-scope dependencies; test roots do not alter production roots, trim records, policy evaluation or claims.
2. Collect isolated compiled test output, generated test classes, and applicable test resources after successful compilation. Include existing explicit roots and supported dynamic-root conventions. Respect the selected test compiler and runtime release, multi-release JAR views and project-provided platform inputs. Never use stale `target/test-classes` as evidence when the current build skipped or failed compilation; use current lifecycle provenance and input fingerprints. `-DskipTests` may still compile tests; `-Dmaven.test.skip=true` normally skips compilation as well. Handle each according to actual execution, not the flag name alone.
3. Reuse the existing indexed archive inventories, bytecode reference graph, transitive cross-artifact closure, pass-through handling and dynamic-root policies. Test closure starts from actual test bytecode alongside the already retained production view and normal test inputs. Do not rescan every JAR once per test class. Test-only references, including ones from a restored class into another removed artifact, must reach a fixed point. Existing library-role indexes may omit method bodies; ensure newly restored classes are analyzed in a role that includes the body edges needed by the existing closure, rather than assuming the library index alone suffices.
4. Compute additions by provider and actual effective class/resource entry, not just class name or a release number. Check that classpath precedence in the resulting runtime view selects the same intended providers as the original mediated test view, and re-evaluate closure against that final view. Do not duplicate classes already present in the selected production provider. Preserve needed original resources and service metadata using the existing archive policies; retain ambiguous or unsupported inputs conservatively. Account for reflection and configuration within the current evidence limits rather than claiming complete dynamic reachability.
5. Build deterministic test-only artifacts outside production output and user dependency caches. Handle dropped whole artifacts, partially trimmed artifacts, classpath resources, duplicate owners, signed or sealed packages, manifests, multi-release entries and service descriptors. Prefer existing archive writers and validation. If a split causes package sealing, module-path, signature, provider-order or resource semantics to change, use a verified test-only whole-artifact replacement or report unsupported. Do not append an original full JAR after a retained trimmed JAR and assume it can replace classes already loaded from the first JAR.
6. Fingerprint test input content, effective production snapshot, test output, runtime view, dynamic-root and overlay semantics. Reuse production indexes and cached test results only for matching inputs and semantics; no stale test output or old overlay may authorize a new test run. Keep runtime-scoped additions under the build directory and out of artifact attachment, installation, deployment, packaging and production provenance.

### Reporting and failure behavior

`analyze` before test compilation reports the production plan and that the test graph is not yet available; it must not predict a successful test overlay from stale output. Successful test preparation reports the test input boundary, original-versus-production dependency changes, added artifacts/classes and whether any conservative fallback was used. Expose deterministic summary and actionable diagnostics in console and, if persisted, a separate test-scoped report or an explicitly distinct report section. `report` replays saved observations without rediscovery and must label unavailable test results; retain existing production snapshot and VEX semantics. Do not publish a test-only addition as a production omission proof or a production vulnerability mitigation. Existing precondition-proof guards remain authoritative, including their `skipTests=true` requirement when the lifecycle reaches Surefire; running tests does not implicitly make that proof eligible.

Direct invocation with incomplete or stale test outputs, absent original inputs, a disabled extension needed for view isolation, or unsupported ordering must yield a clear error or an explicit non-analysis result appropriate to the invoked goal. Never claim test coverage or allow original test compilation paths to become the production package view. Respect existing behavior of `analyze` and `elide` when the test lifecycle is not requested.

## Concrete implementation and TDD plan

For each slice, write behavioral tests first, run them and verify the intended failure, implement the minimum, and rerun. Share immutable fixtures and executions where compatible and aggregate independent assertions. The implementation uses existing production algorithms; this ADR does not authorize a second production compilation or a new method-level call graph.

1. **Lifecycle proof and view selection.** Construct a local dependency containing a production `Client`, test-only `Builder`, transitive builder helper, and unused class. Compile a consumer against it; the main application uses only `Client`, while a JUnit test uses `Builder`. Demonstrate the current clean-build test compilation failure with production trimming enabled. Prototype the two Maven integration candidates above; prove which artifact files are visible when the compiler Mojo is configured, restore on success and failure, and check a fresh resolver request plus package after tests. Prove an originally dropped whole artifact used by tests separately. Cover Maven's `maven.test.skip`, `skipTests`, direct goals, no test sources, multiple test executions, cache hits, `clean`, a normal compiler annotation processor, standard classpath and reactor leaf behavior. The actual Maven fixture is the acceptance authority; mocks of a project artifact set alone are insufficient.
2. **Capture original and effective views.** Extend `MavenElisionOutputPublisher`, `MavenArtifactPlan`, `MavenAnalysisResolutionContext` and the lifecycle resolver-plan bridge as needed so test compilation uses immutable original *allowed* inputs and packaging continues to resolve the exact effective production projection. Do not conflate audit-only original ban inputs with allowed inputs. Test matching coordinates with distinct scopes, duplicate declarations, a transitive dropped dependency, `provided`, `runtime` and `test` scopes, classifier identity, detached original paths, original file immutability and a version conflict mediated by Maven. Observe the resulting compiler classpath and packaging tree from actual plugins.
3. **Test graph and overlay.** Make the existing `ElisionReachabilityEngine`, relevant inventory/closure machinery and archive reader/writer reusable for a test scope without introducing production roots. Start with failing tests for the builder, an entire dropped artifact, a multi-hop cross-JAR link, a test-only dynamic or service root, and ordinary test dependencies. Assert actual test execution and exact original-provider entries in the overlay. Exercise duplicate class owners, resources, reflection configuration, sealed or signed inputs, multi-release views, unsupported modular cases, fallback diagnostics, unchanged original bytes and incomplete input handling. Where trimming is disabled or no test-only addition is needed, avoid needless graph/archive work.
4. **Delivery, lifecycle and reporting.** Integrate the supported test runner with test-only entries after compilation and before execution, preserving user configuration. Verify classpath order and class origins at runtime, two distinct Surefire executions with different existing configuration, clean/reset behavior and no stale overlay across changed tests, dependencies or production snapshots. Confirm compilation failures or interrupted/partial lifecycles do not leave production resolver or artifact views altered. Test `analyze` before tests, Elide, separate test report persistence/replay, and unavailable/fallback states. Confirm production forbidden-code results, SBOM and VEX are not reclassified by test-only content, and existing `skipTests` precondition-proof guards still apply.
5. **Packaging acceptance.** Use a real packaged application with a dependency-consuming packager such as Maven Shade and inspect its artifact contents and dependency tree, not only a plain application JAR, which does not embed dependencies. Assert `Client` is present, `Builder`, its helper and the dropped test-only artifact are absent from production artifacts, and tests still pass. Compare package output, resolver tree and production SBOM between separate clean builds using `-Dmaven.test.skip=true`, `-DskipTests` and running tests. Assert the first build did not compile tests or prepare additions; `skipTests` alone is not an independent no-overlay baseline because test compilation may still run. Cover a fresh dependency-resolution request after tests and fail if original JARs or synthetic test additions are selected. Verify an isolated packaged-application smoke test separately; do not use the overlay as proof of production closure.
6. **Examples and documentation.** Add or extend a reproducible example with a local dependency and a test-only builder and helper. Demonstrate original compilation, production trimming, successful test compilation and execution, the reported test-only addition, and inspection of the packaged production result. Cover a fully dropped artifact as well as a class removed from a retained artifact. Add the example to the existing harness and generated transcripts. Update the homepage [README](../../README.md), plugin [usage](../../dependency-elider-maven-plugin/src/site/markdown/usage.md), and [FAQ](../faq.md) with the lifecycle, actual supported Maven/runner/module boundaries, test-classpath consequence, conservative fallback and packaging guarantee. Clearly label planned behavior until implemented. Run `make update-transcripts` for changed fixtures or displayed output, review generated blocks and run `make check-transcripts`.
7. **Verification.** Run targeted tests, then `make check-fast` and full `make check`, plus `make test-examples` and transcript checks when the example changes. Test on standard compliant JDK 21+ without an exact vendor or patch requirement. Follow repository rules for differential tests and JMH when adding custom parsing or optimization.

### Implementor's execution checklist

Perform these steps in order. Do not start the graph implementation until the Maven fixture proves the handoff. Record exact command lines, observed file paths and exit statuses in RQ-0017; a proposed callback is not evidence that Maven invokes it at the required time.

1. **Find the existing integration seams.** Read `DependencyContextLifecycleIT` and its consumer-fixture helpers, `EliderLifecycleParticipant`, `ResolverArtifactPlanPublisher`, `EliderRepositorySessionDecorator`, `MavenArtifactViewUpdater` and `MavenElisionOutputPublisher`. The existing resolver plan is scoped by project base directory plus GAV; its payload crosses extension/plugin classloader boundaries as JDK-only collections and scalar values. If a test-view handoff crosses those realms, follow that pattern and the repository's independent schema-version rule rather than sharing plugin-specific instances. Do not modify the existing production resolver plan for a test-only overlay.
2. **Make the first failure reproducible with Elider.** Start from the local experiment in RQ-0017, then extend the existing packaged Maven fixture or add a focused `ADR0016TestViewIT` alongside it. Install a local fixture library with `Client`, `Builder`, `Helper` and `Unused` classes, and a small second artifact used only by the test. The app calls `Client`; its test constructs `Builder`, which uses `Helper` and the second artifact. Configure actual production trimming and a packaging consumer that bundles dependencies. On the current Elider implementation, assert the clean lifecycle fails specifically because `Builder` or the test-only artifact is missing from the test compiler's actual classpath. Inspect the production trim to ensure the example truly removed those classes; do not accept a failure caused by missing Maven plugins, test framework setup or a wrong fixture.
3. **Prove one compiler-view handoff.** Implement the smallest test-only prototype in the lifecycle fixture or its helper extension. Record the original allowed mediated GAV/type/classifier, scope, file and order before production mutation. Demonstrate that the selected Maven callback runs after test dependency resolution but before the compiler's `${project.testClasspathElements}` injection, that the compiler sees original `Builder`, and that the project artifact objects and resolver projection are restored after the compiler. Test a deliberate source compilation error and check post-failure evidence using an independent probe where Maven's failure handling permits it. Show a normal direct/partial lifecycle that does not run the compiler leaves the production view intact. Prove callback registration and listener chaining in a real Maven process; do not assume an exception thrown from `EventSpy` fails the build.
4. **Prove test-runtime delivery independently.** Before implementing reachability, generate one hand-built additions JAR containing only `Builder` and `Helper`, plus any required second artifact. Arrange for the actual Surefire execution to use it. Assert from inside the test that `Client` comes from the trimmed production JAR and `Builder` from the additions JAR; verify an intentionally omitted helper fails before adding it. Capture the actual Surefire classpath and preserve existing user-provided additional elements, including a second Surefire execution with different settings. This proves the Maven delivery mechanism separately from the graph's correctness.

## Questions and answers

1. **Why preserve original inputs for test compilation?** At `process-classes`, test bytecode does not yet exist, and test-only builders may already have been removed from the production view.
2. **Are tests compiled twice?** No. Compile production once, trim, and compile tests once against their appropriate original test view.
3. **Does the existing mediated TEST graph solve this?** No. It identifies Maven dependencies, not the classes used by compiled tests.
4. **Do we need a new reachability algorithm?** No. Reuse the existing class-level closure and dynamic-root behavior with test roots and original test inputs; only view selection, the difference and delivery are new.
5. **Can we just add originals with `test` scope?** Not as a second `DefaultArtifact` of the same identity in Maven 3's artifact set: equality ignores scope and file. Investigate distinct temporary test-only entries or compiler integration as alternatives; Elider's scope-independent replacement and the fact that test scope persists through execution also need handling. Prove actual behavior before relying on either route.
6. **Do tests prove the package complete?** No. The ordinary Maven test classpath and these additions can supply classes absent from deployment; the graph and packaged-app testing provide separate evidence.
7. **Does test-only code enter the production package or VEX?** No. Packaging, the production graph, SBOM and VEX keep the verified production view.
8. **What happens when static analysis is incomplete?** Preserve more code in the test view or use a safe test-only replacement with a visible explanation. If that cannot be done safely, fail test preparation rather than change production or claim completeness.
9. **What about banned dependencies?** The preserved original test view comes from the allowed mediated graph after explicit ban policy, never the separate audit-only original graph. Conflicts between a test and an explicit ban are reported, not silently bypassed.
10. **What remains open?** The Maven hook and view handoff, exact report schema and automatic activation, supported compiler/test runner versions, arbitrary JPMS/module-path behavior, and integration-test runner handling require the lifecycle proof and focused follow-up. Record implementation findings in RQ-0006, RQ-0017 and RQ-0018 as applicable.

## Consequences

Tests can use dependencies and classes not required by production without increasing the production artifact. Tests still exercise the retained production classes for ordinary overlays. The build pays for test usage analysis and may need additional temporary artifacts; difficult archive or Maven configurations may require a conservative test-only replacement or an explicit unsupported result. The production compilation, production graph, package contents and existing evidence boundaries remain unchanged.
