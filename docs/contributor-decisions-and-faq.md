ADRs remain the authority for accepted architecture; research questions track unresolved investigations. User configuration and product concerns belong in the [User FAQ](faq.md), which summarizes relevant outcomes without internal implementation detail.

## Engineering FAQ

### Maintaining command transcripts

Transcript commands require Go 1.24 or later, Java 21, the Maven wrapper, `curl`, and GNU `timeout`. CI pins Go and Java; local setup should use matching toolchains. The runner reads [`scripts/transcripts-manifest.json`](../scripts/transcripts-manifest.json), which declares each command, working directory, arguments, expected goal and exit status, target document, and optional output evidence requirements. Each target document contains one exact `BEGIN`/`END` marker pair per invocation. `{root}` and `{evidence}` are expanded to the repository and per-run evidence paths; generated commands display these as `$PROJECT_ROOT` and `$TRANSCRIPT_EVIDENCE`.

The runner removes only known Maven scan/build boilerplate. It normalizes the Snapshot `last successful elide run at` timestamp, Maven `Total time` and `Finished at` values, PID fields, the exact repository root and generated evidence directory, and trailing whitespace. Repository/evidence path substitutions preserve path suffixes; unrelated timestamps and temporary paths remain visible. Report output retains three graph rows and replaces further graph rows with a count and SHA-256 digest. Rerun the displayed fixture's `report` command to see the full graph; a dedicated expansion target remains deferred. The local CVE cache at [`scripts/fixtures/transcript-vulnerability-cache/index.json`](../scripts/fixtures/transcript-vulnerability-cache/index.json) pins two selected mappings for stable examples; it is intentionally incomplete, and `HIGH` describes mapping confidence rather than symbol coverage. Baseline packaging can resolve Maven dependencies from configured repositories; analysis and elision use the copied cache with Maven offline mode.

Run `make update-transcripts` to regenerate all configured output blocks. It validates every command and marker before writing any documentation. Run `make check-transcripts` to compare generated blocks without rewriting tracked documents; Maven `target` directories, the local repository, and ignored `.scratch` evidence may still change. `make check` runs this check serially after other Maven checks to avoid concurrent writes.

### Why do the examples use `elide.mode` while the plugin exposes `elide.skip`?

`elide.mode=baseline|elision` names the two fixture behaviors and activates the example's `elision` Maven profile by property. The profile maps the `elision` mode to the plugin's internal `elide.skip=false` setting. This keeps each fixture's dependencies and packaging configuration in one POM while making baseline and elided builds easy to compare. General plugin users continue to control the goal with `elide.skip`.

### Can we keep all multi-release entries and analyze only the base classes?

The trimmer does not analyze only the base classes. It elevates and trims the compiler target view, preserves all higher class entries, and analyzes tier-specific bodies through the Maven runtime release to retain their intra-JAR and sibling dependencies. Tiers above the Maven runtime are preserved without verified linkage to sibling JARs.

### Can ProGuard Core scan our Java sources instead of the source scanner?

No. ProGuard Core handles classfiles and their references. Java source attribution is a separate compile-time concern, so the plugin keeps a source scanner for source roots and ProGuard Core for bytecode link closure.

### What happens when a dependency calls `MethodHandle` or `VarHandle` with a custom descriptor?

The JVM defines these as signature-polymorphic calls. Their call-site descriptor may differ from the declared method descriptor, but every class named by that descriptor must still resolve. The trimmer recognizes only the JVM-defined declarations and adds those descriptor types to closure; bogus names, missing descriptor classes, and unrelated missing members remain errors. See [JVMS §2.9.3](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-2.html#jvms-2.9.3) and [§5.4.3.3](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.4.3.3).

### Why can the direct and resolved Maven dependency views differ?

The current tested same-session path preserves the direct set so Maven does not re-resolve the original graph, while classpath and packaging consumers use the pruned resolved view. A direct-view plugin may still report an elided dependency. If both views are pruned, the tested Maven 3.9.11 lifecycle resolves the original POM graph again and restores original classpaths. See [RQ-0006](research/RQ-0006-maven-artifact-view-consistency-and-early-resolution-hooks.md) for impact tests and earlier-hook options.

### What did platform snapshot reuse improve, and what remains expensive?

The JMH fixture measures production `MavenDependencyTrimmer.trim` for one tiny candidate, including dynamic roots, dependency digests, cache-manifest validation, and cached-output hashing. A warmed request measured 0.093 ±0.001 ms/op; a fresh request with the existing output cache measured 93.465 ±0.391 ms/op. The warmed repeated request is below the <10 ms budget; a fresh-context cache hit is about 9.3× above it, and neither operation represents a whole Maven invocation. Slice 7.6 keeps normalized platform paths, selection evidence, JMOD inventory, and one exact SHA-256 per selected source. On the tested GraalVM 21 JDK, that identity covered 81 sources and held zero archive byte arrays; its serialized text was 17,805 characters, not an exact heap measurement. JFR profiles are sampled and include setup/warmup; they do not provide exact CPU or allocation totals. A targeted single-Maven-process Spring run peaked at 3,119,312 KiB RSS with 485 samples at 50 ms; child processes were excluded. Three post-7.6 example cycles had median paired differences of +1.977 s Basic and +20.417 s Spring. The initial 7.6 implementation measured 96.488 ms/op before removal of the redundant JMOD central-directory preflight; that removal reduced fresh JMH by about 3 ms, while end-to-end examples were not rerun after that small change. These results are descriptive, not isolated causal claims. Slice 7.7 remains a candidate for measurement after feature acceptance. See the [follow-up handover](handovers/2026-10-26-performance-follow-up.md) and [RQ-0003](research/RQ-0003-sub-10ms-maven-fast-path-invariant-and-benchmarking.md).

### What can be reused across graph contexts?

The archive snapshot reuses immutable symbolic declarations for metadata-free sibling classes. Each graph gets new mutable ProGuard classes, members, reference arrays, and a context-local initialized pool. Kotlin metadata classes are reparsed from snapshot-owned bytes because ProGuard mutates their metadata while linking; malformed metadata still fails closed. Resolved references and pools are not shared.

### Why is the Spring elision Maven build much slower than baseline?

Three post-7.6 baseline-first `clean verify` cycles measured median baseline/elision times of 2.262/4.224 s for Basic and 4.106/24.523 s for Spring Boot. The median paired differences were +1.977 s and +20.417 s respectively, close to the 6.6 checkpoint's +1.972 s and +20.337 s; the comparison does not isolate one slice's effect. Separate JFR/RSS profiles and final warmed-versus-fresh JMH operations are recorded in RQ-0003; warmed request reuse is below <10 ms, while fresh capture and representative single-project invocations remain costly.

### How do I measure elision's end-to-end Maven cost?

Run `make test-examples`. It times matched `clean verify` invocations for the Basic and Spring Boot examples with elision skipped and enabled, and prints the difference. This includes Maven startup, dependency resolution, compilation, tests, the elider, and packaging; trace capture and running/verifying the final application are outside the timed calls. A direct `mvn dependency:tree` does not invoke the `initialize` lifecycle phase, so it cannot measure the elider. The current medians use three runs and remain specific to the GraalVM 21 environment; see [RQ-0003](research/RQ-0003-sub-10ms-maven-fast-path-invariant-and-benchmarking.md).

### What happens when metadata or an archive layout is unknown?

Fail closed before Maven artifact pointers change, unless the policy explicitly classifies that artifact as unchanged/pass-through. Unknown dynamic class metadata is not treated as an empty root set. `elide.mrjarStrategy=pass-through` preserves an MRJAR unchanged; it does not make malformed archive layouts safe to skip or protect sibling dependencies referenced by unanalysed tiers.

### Why not shade everything into one JAR before analysis?

Each dependency remains a distinct JAR keyed to its Maven coordinate. This preserves per-artifact provenance, digest accounting, class ownership, and the ability to report which dependency changed.

### How are advisories with multiple vulnerable classes handled across version ranges?

Currently, `OmittedCodeProof` requires that all mapped vulnerable classes exist in the original JAR (`originalArchiveClasses.containsAll(vulnerableClasses)`). If an advisory maps multiple classes but the target artifact version does not contain all of them, proof fails closed.

For example, in Jackson Core (`CVE-2026-68494` / `GHSA-r7wm-3cxj-wff9`), the fix commit touches both `com.fasterxml.jackson.core.async.ByteArrayFeeder` and `com.fasterxml.jackson.core.exc.StreamConstraintsException`. The advisory marks Jackson Core versions `(,2.18.8)` as vulnerable. However, `StreamConstraintsException` was only introduced in Jackson 2.15.0; older vulnerable versions (such as 2.14.x) lack that class entirely. Under the current strict rules, an elision proof for Jackson 2.14.x cannot be established. We are still evaluating what multiple vulnerable classes mean semantically (e.g., whether presence of any class indicates exposure or whether all must interact) and whether the engine should remain as strict as it is today.
