## Engineering FAQ

### Why do the examples use `elide.mode` while the plugin exposes `elide.skip`?

`elide.mode=baseline|elision` names the two fixture behaviors and activates the example's `elision` Maven profile by property. The profile maps the `elision` mode to the plugin's internal `elide.skip=false` setting. This keeps each fixture's dependencies and packaging configuration in one POM while making baseline and elided builds easy to compare. General plugin users continue to control the goal with `elide.skip`.

### Can we keep all multi-release entries and analyze only the base classes?

No. Keeping the bytes avoids changing that JAR, but base-class references may omit calls made by the effective versioned class body. Use an effective runtime view and treat its classes as roots for cross-artifact closure, or compute a union across all supported variants. Otherwise a referenced class in another trimmed JAR can still be removed.

### Can ProGuard Core scan our Java sources instead of the source scanner?

No. ProGuard Core handles classfiles and their references. Java source attribution is a separate compile-time concern, so the plugin keeps a source scanner for source roots and ProGuard Core for bytecode link closure.

### What happens when a dependency calls `MethodHandle` or `VarHandle` with a custom descriptor?

The JVM defines these as signature-polymorphic calls. Their call-site descriptor may differ from the declared method descriptor, but every class named by that descriptor must still resolve. The trimmer recognizes only the JVM-defined declarations and adds those descriptor types to closure; bogus names, missing descriptor classes, and unrelated missing members remain errors. See [JVMS §2.9.3](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-2.html#jvms-2.9.3) and [§5.4.3.3](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-5.html#jvms-5.4.3.3).

### Why can the direct and resolved Maven dependency views differ?

The current tested same-session path preserves the direct set so Maven does not re-resolve the original graph, while classpath and packaging consumers use the pruned resolved view. A direct-view plugin may still report an elided dependency. If both views are pruned, the tested Maven 3.9.11 lifecycle resolves the original POM graph again and restores original classpaths. See [RQ-0006](research/RQ-0006-maven-artifact-view-consistency-and-early-resolution-hooks.md) for impact tests and earlier-hook options.

### What did platform snapshot reuse improve, and what remains expensive?

The post-7.5 JMH fixture measures a warmed request's production trim-cache operation at 0.094 ms/op, below the <10 ms repeated-request target. A fresh request with an existing output cache takes 1,172.372 ms/op because it captures platform identity; JFR sampled SHA-256 and SHA-1 heavily. Retaining the selected `ct.sym`, release metadata, and JMOD contents also kept 130,382,660 bytes per request. In three matched example cycles, end-to-end overhead medians were +3.342 s for Basic and +21.912 s for Spring Boot, above the prior 6.6 checkpoint; this comparison does not isolate 7.5 causality. Planned slice 7.6 keeps paths, selection evidence, and exact SHA-256 identity without retaining archive bytes or computing platform SHA-1. See the [follow-up handover](handovers/2026-10-26-performance-follow-up.md) and [RQ-0003](research/RQ-0003-sub-10ms-maven-fast-path-invariant-and-benchmarking.md).

### What can be reused across graph contexts?

The archive snapshot reuses immutable symbolic declarations for metadata-free sibling classes. Each graph gets new mutable ProGuard classes, members, reference arrays, and a context-local initialized pool. Kotlin metadata classes are reparsed from snapshot-owned bytes because ProGuard mutates their metadata while linking; malformed metadata still fails closed. Resolved references and pools are not shared.

### Why is the Spring elision Maven build much slower than baseline?

Three post-7.5 baseline-first `clean verify` cycles measured median baseline/elision times of 2.269/5.611 s for Basic and 4.125/26.037 s for Spring Boot. Elision added +3.342 s and +21.912 s respectively, compared with the 6.6 checkpoint's +1.972 s and +20.337 s. Several slices and environment state differ, so this does not isolate 7.5's effect. Separate JFR/RSS profiles and warmed-versus-fresh JMH operations are recorded in RQ-0003; the 7.5 warm operation meets <10 ms, while fresh capture and representative single-project invocations remain costly.

### How do I measure elision's end-to-end Maven cost?

Run `make test-examples`. It times matched `clean verify` invocations for the Basic and Spring Boot examples with elision skipped and enabled, and prints the difference. This includes Maven startup, dependency resolution, compilation, tests, the elider, and packaging; trace capture and running/verifying the final application are outside the timed calls. A direct `mvn dependency:tree` does not invoke the `initialize` lifecycle phase, so it cannot measure the elider. The current medians use three runs and remain specific to the GraalVM 21 environment; see [RQ-0003](research/RQ-0003-sub-10ms-maven-fast-path-invariant-and-benchmarking.md).

### What happens when metadata or an archive layout is unknown?

Fail closed before Maven artifact pointers change, unless the policy explicitly classifies that artifact as unchanged/pass-through. Unknown dynamic class metadata is not treated as an empty root set. Multi-release target pass-through is a specific exception, with strict failure available; it does not imply that every unsupported archive shape is safe to skip.

### Why not shade everything into one JAR before analysis?

Each dependency remains a distinct JAR keyed to its Maven coordinate. This preserves per-artifact provenance, digest accounting, class ownership, and the ability to report which dependency changed.
