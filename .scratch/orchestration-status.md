## Baseline decisions and known risks (current implementation status is recorded below)

- No new owner/proof hierarchy or confidence marker. Confidence is descriptive. Only current validated effective-POM owner assertions may enter the existing proof-specific APIs.
- GAV plus a source-JAR coordinate is not source/binary identity. Proof requires exact original binary bytes and exact source bytes to be connected by a reproducible build; arbitrary caller-supplied reproduction cannot create capability. A source archive coordinate is only a locator, not proof that those bytes generated the assessed artifact.
- Resolve a `programFiles` source path only by an exact path in the identified source archive or by the explicit conventional-layout assumption. This was disabled at the initial baseline; S2 now implements exact source-classifier lookup plus pinned source/build reproduction and is reviewed GO. A basename or `SourceFile` match remains corroboration only; S2 correspondence alone still cannot create proof authority.
- Reproduction is a set of separately tracked compilation tasks, one per source unit, with annotation processors and compiler plugins disabled. Every task must use an explicitly supported classpath/compiler configuration. The union of emitted class entries must form a bijection with the source-attributed class output set, and each emitted class's bytes must equal the corresponding exact original archive entry bytes. Missing, extra, ambiguous, or byte-different output blocks proof.
- `JavaFileManager` sibling/origin callbacks are not a portable provenance guarantee and cannot be used as the completeness oracle. Completeness comes from recorded source units and reproduced class bytes, not compiler callback behavior.
- Initial compiler support is deliberately narrow: the exact pinned Oracle GraalVM 21.0.12+7.1 `javac` image only. Its loaded javac class, `jmods/jdk.compiler.jmod`, `lib/modules`, and `lib/ct.sym` bytes are SHA-256-bound and checked against the fixed allowlist once per assessment invocation. Nonempty original-JAR manifest `Class-Path` is rejected. Until each combination is covered, other JDK images, compilers, releases, flags, processors, plugins, generated sources, and transformations abstain. This is not a claim of general Java compiler support.
- Unknown range applicability blocks proof. Cached/advisory evidence never restores proof authority.
- Routine names can be overloaded or repeated. A layout assumption cannot bypass completeness. Stale proof bytes block publication.
- Initial support may be limited to non-MRJAR Java builds only where the complete emitted class inventory is reproduced. MRJAR, generated-source, and transforming builds remain review-only unless every tier/output is proven. Existing MRJAR physical safeguards must remain intact.

### S1 claim and identity contract

S1 uses raw source claims as the only applicability authority. `OsvAffectedPackage.versions`, `ranges`, and ordered range events plus each raw CNA product entry's `versions` and `defaultStatus` determine applicability. Per [OSV data documentation](https://google.github.io/osv.dev/data/) and the [OSV schema](https://ossf.github.io/osv-schema/), a version is included when explicitly listed **or** when it falls in a supported affected range; these are alternative/compact encodings, not an intersection. Preserve each OSV `affected[]` package entry and each CNA product entry independently because entries can encode package/platform distinctions. If multiple entries apply to one candidate without an unambiguous identity/platform selection, return `UNKNOWN`; do not flatten or union ambiguous entries. `AdvisoryScope.versionRangeSpec` is a compatibility/report projection only; it must never authorize automatic candidate matching or proof. The shared core evaluator returns exactly `AFFECTED`, `UNAFFECTED`, or `UNKNOWN`; proof eligibility requires both the selected OSV package and exactly one selected CNA product entry to evaluate `AFFECTED` for the same concrete Maven version. Any unknown, unsupported, malformed, overlapping, conflicting, or ambiguous claim evaluates `UNKNOWN` or is rejected before evaluation.

The CNA version rules follow the official [CVE 5.0 product and version encoding](https://github.com/CVEProject/cve-schema/blob/main/schema/docs/versions.md): affected product objects remain separate; version objects for one product are required to describe disjoint sets; a missing `defaultStatus` means `unknown`; a single-version object has only `version` and `status`; a range requires `versionType` and exactly one upper bound; `lessThan` is exclusive and `lessThanOrEqual` inclusive; `changes` refine a range at ordered `at` versions and clients must order them with that version type before evaluation. S1 supports only `versionType: maven` for range claims. `custom`, Git/source-control, other ecosystems, unknown status, bad bounds/change ordering, overlap, or any unresolved conflict cannot be treated as affected. A concrete exact-version claim may be evaluated as a single-version claim, but malformed extra range fields do not become ignorable merely because the `version` string equals the candidate.

Product identity must bind the actual artifact's full GAVCE. A parsed Maven PURL uses namespace as groupId and name as artifactId; its `type` defaults to `jar`, and classifier is optional. Any supplied version, type, classifier, qualifier, or subpath must be supported and agree with the candidate coordinate; absent attributes may use only an explicit, documented claim/default basis, otherwise identity is `UNKNOWN`. A `packageURL` containing unsupported qualifiers/subpaths or contradicting the other identity claims is refused. An alternative `collectionURL` plus `packageName` route is allowed only for a recognized collection identity with an unambiguous Maven `group:artifact` encoding. Vendor/product display names, names alone, or one identity source that contradicts another never match. `cveMetadata.cveId` must equal the requested CVE ID/OSV alias and `cveMetadata.state` must be `PUBLISHED`; mismatched or non-published CVE records cannot contribute structured claims.

## Architecture decisions and review findings

- The session architect independently reviewed the dirty snapshot and authorized a dual-layer design. Its key finding is that collection-time exclusions erase the banned node and descendants before current inventory capture; post-resolution leaf-drop logic alone cannot prove retained content has no links to those providers.
- Freeze original effective declaration/exclusion inputs and provenance before mutation. Inject only after all selected projects pass policy preflight. Resolve an isolated original-input audit inventory at goal execution, bypassing Elider replacement/projection and graph-store recording. Keep audit providers as evidence inputs, never deployment graph members; fail explicitly if audit cannot be established.
- Keep actual post-injection graph separate for `EffectiveGraphPolicy`, ancestor protection, output projection and identity.
- Reject a ban matching any effective first-level declaration or actual direct artifact-view member, with or without extension. Successful bans are transitive and already absent from the direct view. Preserve ADR-0002 direct membership.
- Both `AnalyzeMojo` and `ElideMojo` must enter the same strict ban validation and effective closure. Do not allow analysis to bypass closure through the existing direct `analyze()->finish` path.
- For process-classes execution, compile against the collection graph after explicit bans but before telemetry pruning/trimming. Fail if compilation/generation or evidence validation cannot establish the selected variant. A completeness assertion does not authorize unknown writers.
- Distinguish unmatched, excluded-before-resolution, and forced-absent-after-resolution. Exclusion recommendations remain read-only. Current unreleased report format remains version 1. No alias or migration for unreleased draft formats.
- Ban validation occurs before promotion, identity creation and publication; use the existing staged publisher boundary. A failed plan must not replace the last successful reports or resolver plan.
- Collection-excluded audit artifacts remain audit-only: raw/effective decisions must still partition the actual post-injection inventory. Keep `excluded_before_resolution`, `forced_absent_after_resolution`, and `unmatched` as distinct policy outcomes and do not inflate graph-drop metrics with audit nodes.
- Add a separate extension-hook marker so a genuinely absent core extension can be distinguished from an active hook with missing/failed capture. A no-extension fallback needs a real plan-free graph pair bound to current inventory; missing or ambiguous graph proof stays fail-closed.
- Analyze validates the same effective plan but does not claim post-resolution removals were applied. It must not reuse `service.finish()` if that bypasses fixed-point closure or commits trim generations; label fallback removal as planned.
- Audit resolution must clear cloned direct/resolved caches, isolate session coordination data, bypass resolver replacement/projection/capture decorators, and leave live views, shared capture, and plan generations unchanged. Preserve the existing staged publisher's output/view/plan rollback sequence.
- External `gemini_review_diff` bridge is unavailable in this environment; record fail-open notice in review receipts and use the architect plus dedicated reviewer.
